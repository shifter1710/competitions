# Решения по модели данных

Актуальное состояние схемы см. в [data-model.md](data-model.md); этот
документ — история решений.

## Смена группы/института/курса студентом

Запись о соревновании — **исторический факт участия**. Группа, институт и курс
в записи отражают то, чем студент был на момент соревнования, и при смене
профиля **не перезаписываются**: в 2024 он выступал за ПГС-101 — так это и
останется в записи и в отчётах за 2024 год.

Текущие значения (ФИО, пол, институт, группа, курс) хранятся в профиле
пользователя (`users.profile_data`) и:

- автоподставляются в новые записи атлета, когда поле не заполнено в форме;
- поле формы всегда имеет приоритет над профилем;
- профиль редактирует сам пользователь (для атлетов — страница «Профиль»).

Отчёт «количество участий» группирует по данным записи, поэтому участие за
разные годы с разными группами попадает в разные строки — это осознанное
поведение: отчёт показывает факты на дату.

Если однажды понадобится массовая правка (например, «привести все записи
студента к текущей группе») — это отдельный админский инструмент с явным
подтверждением, не автоматика.

## Личность и смена фамилии

Якорь личности — аккаунт. У аккаунта есть список ФИО-псевдонимов
(`users.name_aliases`):

- каждое ФИО из профиля автоматически дописывается в псевдонимы (список
  только растёт), поэтому смена фамилии ничего не отрывает;
- админ может привязать дополнительное ФИО к аккаунту вручную
  (`POST /admin/users/<id>/alias`) — для истории, заведённой под старой
  фамилией до создания аккаунта;
- кабинет атлета = свои записи + записи с `student_id` из хешей любых
  его псевдонимов.

Отчёт «количество участий» группируется по данным записи (student_id +
ФИО + группа + курс — исторические факты). Чтобы смена фамилии не
дробила человека в цифрах, есть админский merge
(`POST /admin/students/merge`): превью показывает, сколько записей
будет объединено; подтверждение переписывает `student_id` старого ФИО на
новое; по умолчанию перезаписывается и отображаемое ФИО записей
(галочка «оставить исторические» отключает). Merge не автоматизируется:
однофамильцы-тёзки существуют, решение остаётся за админом.

## Привязка существующих записей к новому аккаунту атлета

Кейс: админ заранее внёс участия человека, потом человеку создали аккаунт
атлета. Связь не требует отдельной кнопки «забрать записи»:

- кабинет атлета показывает записи `owner_id = <атлет>` **или**
  `student_id = sha256(ФИО из профиля)`;
- при пустом ФИО в профиле атлет видит только собственные записи;
- правила правок при этом не меняются: правка атлета (включая «свою по
  ФИО» запись, созданную админом) отправляет запись на повторную проверку;
  правка модератора — подтверждает. Решение по роли, а не по владельцу;
- при смене ФИО в профиле состав «подтянутых» записок меняется вместе с ним.

## Подсказка ФИО и приватность (2026-09-12)

Полный список ФИО из записей (`GET /api/students`) доступен только
admin/editor — оператору он и так виден в таблице. Атлету список чужих
ФИО не отдаётся: только точечная проверка своего ФИО
(`GET /api/students/lookup?name=` → `found` true/false), чтобы атлет
не мог перебором узнать участников. Подсказки-список (datalist) — только
в админских формах (merge-секция, привязка псевдонима); в профиле атлета —
текстовая строка «найдено/не найдено» без раскрытия чужих данных.

## Тёзки (одинаковые ФИО у разных людей)

Принято: не обрабатывать заранее. Влияние ограничено: в отчёте тёзки и так
склеены (исторически так было с группировкой по ФИО); в кабинете тёзка-атлет
увидит записи двойника (просмотр, не порча); правка «своей по хешу» записи
тезки уходит на модерацию, модератор — страховка. При реальном случае
(жалоба «в кабинете чужая запись») — точечно: снять лишний псевдоним или
усложнить привязку подтверждением админа.

## Аудит-журнал безопасности (2026-09-12)

Новая таблица `audit_log` (append-only, записи только добавляются, не
редактируются и не удаляются из UI): `id, created_at, user_id, username,
action, details`. Фиксируемые события (минимальный набор):

- `login_success` / `login_failed` — входы (username при неудаче пишем,
  user_id может быть пустым);
- `password_changed` — смена пароля (кем и чьего аккаунта);
- `record_approved` / `record_rejected` — решения модерации с комментарием;
- `students_merged` — merge с параметрами (from_name, to_name, счётчик,
  rewrite_names);
- `alias_added` — привязка ФИО к аккаунту администратором.

Просмотр — страница `/admin/audit`, только admin, последние записи сверху,
без редактирования. Журнал — инструмент разбора инцидентов, не база для
отчётов: без пагинации на первом шаге (см. пункт 4 бэклога про триггер
объёма). *(Актуализация 2026-09-20: пагинация уже есть — 50 записей на
страницу плюс фильтры по пользователю, действию и периоду.)* Решения по
роли/статусу записей в журнал не пишутся точечно —
их покрывают `record_approved`/`record_rejected` при явном ревью, а правка
с авто-подтверждением модератора фиксируется как `record_approved`.

## Merge и псевдонимы (2026-09-12, по наблюдению QA)

QA-прогон выявил: `merge` с `rewrite_names` переписывал `student_id` записей
на хеш нового ФИО, но не трогал `users.name_aliases` — записи выпадали из
кабинета атлета, пока админ вручную не привяжет новое ФИО. Признано багом,
а не задуманным поведением: кабинет должен переживать merge без ручной
перевязки.

Решение: при выполнении `POST /admin/students/merge` автоматически
дописывать `to_name` в `name_aliases` каждого аккаунта, у которого среди
псевдонимов есть `from_name` (принцип «список псевдонимов только растёт»
не нарушается — ничего не удаляется). `from_name` из псевдонимов НЕ
удаляется: старое ФИО остаётся в истории аккаунта. Обратная ситуация
(записи, созданные под новым ФИО до merge) не меняется. Тест: merge
`from_name`→`to_name` при аккаунте с псевдонимом `from_name` — после
слияния записи видны в кабинете атлета.

## Хранение и схема: SQLite остаёмся, базовые поля не расхардкоживаем (2026-09-12)

Обсуждался переезд с SQLite и перевод базовых полей записи (ФИО, пол,
институт, группа, курс, вид спорта, дата, уровень, название, место) в
управляемую схему. Решение:

- **SQLite остаётся.** Один инстанс на организацию, один оператор, объём
  — тысячи записей в год; WAL уже включён. Переезд на серверную СУБД даёт
  ноль продуктовой ценности сейчас и стоит: деплой-сложность (сервис,
  бэкапы, миграции), переписывание storage-слоя, двойные тесты. Триггеры
  для пересмотра — те же, что у пагинации (п.4 бэклога): реальный рост
  нагрузки или несколько воркеров с общей БД.
- **Базовые поля остаются в коде.** Расхардкод = единый реестр полей поверх
  существующих кастомных: затрагивает build_competition, импорт/экспорт
  xlsx, отчёты, автоподстановку из профиля, все шаблоны и 99 тестов —
  это дорогая переработка с высоким регресс-риском ради гипотетической
  пользы. Домен стабилен: эти поля одинаковы у любого вуза. Потребность
  «ещё поле» закрывается кастомными полями (label, тип, обязательность,
  показ в таблице/экспорте). Управление **значениями**-справочниками
  (уровни, виды спорта, институты) — отдельная дешёвая задача (п.12
  бэклога), её делаем. К реестру полей вернуться — только если появится
  вторая организация с другой базовой структурой.

## Очистка и выгрузка базы (2026-09-12)

Очистка — только admin, в два шага: выбор объёма + ввод подтверждающей
фразы в поле (не confirm()). Варианты очистки по возрастанию ущерба: 1) только вложения,
2) только записи, 3) записи + вложения («всё»). Дополнительно — очистка
по дате: «записи с датой соревнования ДО указанной» (решение
2026-09-13: критерий — дата соревнования, а не дата создания записи),
с галочкой «вместе с их вложениями» (по умолчанию включена).

Перед любой очисткой автоматически создаётся архив удаляемого
(решение 2026-09-13): xlsx удаляемых записей (все колонки, как экспорт)
+ zip их вложений; лежит в data/backups, скачивается со страницы
обслуживания. Это страховка от «очистил и пожалел» — отдельно от
штатных бэкапов по таймеру. Пользователей, кастомные поля,
справочники и сам журнал аудита очистка не трогает; каждое выполнение
пишется в аудит с параметрами. Выгрузка базы — xlsx «всё в одном файле
по листам» (записи, пользователи+псевдонимы, справочники) + существующие
выгрузки остаются.

## Справочники значений (2026-09-12)

Управляем админом — значения, не схема. Принципы:

- Записи остаются свободным текстом (историчность): справочник НЕ
  валидирует и не перезаписывает значения в существующих записях.
- Справочники «Виды спорта» и «Институты» ведут себя как уровни сегодня:
  новое значение из записи/импорта автоматически попадает в справочник;
  админ может скрыть значение (скрытое не показывается в подсказках форм,
  но остаётся в записях и отчётах) или добавить значение руками.
- Назначение — подсказки (datalist) в формах и порядок в списках, не
  контроль. Место — страница «Справочники» в админке; уровни переезжают
  туда же из /admin/levels (старый URL остаётся рабочим).

## Удаление пользователей (2026-09-12)

`POST /admin/users/<id>/delete`, только admin. Семантика:

- Записи — исторические факты: при удалении аккаунта НЕ удаляются,
  `owner_id` обнуляется; запись остаётся в таблице, отчётах и выгрузках.
- Псевдонимы ФИО и привязка кабинета исчезают вместе с аккаунтом
  (ожидаемо: якорь личности удалён).
- Журнал аудита не трогается (append-only; события хранят username
  текстом и переживают удаление).
- Блокировки: нельзя удалить себя; нельзя удалить последнего активного
  админа. Подтверждение — ввод логина в поле (как wipe с фразой).
- Каждое удаление — audit-событие `user_deleted` (кто, кого, сколько
  записей отвязано).

Автогенерация паролей — UI-фича формы (криптослучайная строка без
двусмысленных символов, показ один раз с копированием), серверных
изменений не требует.

## Справочники: институты содержат группы (2026-09-13)

К одному институту относится N групп. Решение: иерархия в
`catalog_values` — записи категории `group` получают parent_id на запись
категории `institute` (группа принадлежит институту; одноимённые группы
в разных институтах — разные записи, уникальность (parent, value)).

- Пополнение парами: пары институт→группа автоматически попадают в
  справочник из записей и импорта (как значения сейчас); админ управляет
  руками на /admin/catalogs (добавить группу в институт, скрыть,
  удалить без записей).
- Формы: выбранный институт фильтрует комбобокс групп до его групп
  (компонент из замечания №4 — комбобокс с фильтрацией). Как и весь
  справочник — ПОДСКАЗКИ, не валидация: свободный ввод остаётся,
  существующие записи не перезаписываются (историчность).
- Миграция: populate пар из существующих записей при обновлении.

Запуск — после влития maintenance-audit (те же файлы).

## Видимость активности пользователей (2026-09-13)

Админ видит на /admin/users, кто онлайн и когда заходил последний раз.

- `users.last_login_at` — успешный вход (обновляется при логине);
  история входов остаётся и в аудите (`login_success`).
- `users.last_seen_at` — активность: обновляется на любом
  аутентифицированном запросе с троттлингом — не чаще раза в 60 с на
  пользователя (защита от write-амплификации на каждый клик).
- «Онлайн» = last_seen в пределах 5 минут (сессии stateless-cookie,
  точного списка живых сессий нет и не заводим — приближение честно
  отображается как «был(а) активен(на)»).
- Колонки на /admin/users: последняя активность (человекочитаемо,
  «3 минуты назад»), индикатор онлайн (зелёная точка). Доступ — admin.

Реализация — после maintenance-audit и иерархии справочников (очередь
по конфликтам файлов).

## Расширение отчётов (2026-09-13, выбор владельца: срезы + метрики + фильтры)

Ограниченный конструктор вместо произвольных таблиц: отчёт
«количество участий» получает:

- параметр «группировать по»: студент (как сейчас) / группа / институт /
  курс / вид спорта / уровень / год — группировка всегда по данным
  записи (исторические факты, смена группы в профиле не склеивает);
- метрики: участия, победы (1 место), призовые (1-3 место);
- фильтры дополняются: институт, группа (после иерархии — с учётом её),
  вид спорта; существующие (ФИО/период/место/уровень/кастомные) остаются;
- выгрузка в Excel — те же срез/метрики/фильтры (расширение существующего
  /export/report с выбором колонок).

Графики на странице — осознанно отложены (Excel закрывает показ;
вернуться при регулярном использовании).

## Переименование значений справочников (2026-09-13)

По инциденту владельца: переименование уровня меняло только строку
справочника, записи хранили старый текст; при следующем импорте старое
значение автодобавлялось обратно — дубли и расхождение. Решение (по
образцу merge): переименование ЛЮБОГО значения справочника (уровень,
вид спорта, институт, группа в пределах своего института) — действие
с превью «затронет N записей» и галочкой «обновить записи» (включена
по умолчанию; снятие — переименовать только справочник). Каждое
переименование — audit-событие catalog_value_renamed (кто, что, во
что, сколько записей обновлено). Для групп переименование затрагивает
пару (институт+группа). Историчность не нарушается: перепись явная,
админская, с подтверждением и следом в аудите.

## Ключ дублей импорта и переименования (2026-09-13, замечание QA)

Дублем импорта считается строка, совпадающая с существующей записью по
ключу (ФИО + дата + вид спорта + название). Следствие: если админ
переименовал с каскадом поле, входящее в ключ (вид спорта, название),
повторный импорт СТАРОГО файла больше не опознаёт его строки как
дубли — они вставятся заново со старыми значениями. Это свойство
определения дубля, не баг; справочник при этом честно пополнится
вернувшимся значением. При переименованиях спортив/названий старые
файлы импорта следует считать устаревшими.

## Реестр полей: лёгкая версия сейчас, полная запланирована (2026-09-13)

Владелец выбрал: сейчас — лёгкая версия (базовые поля остаются системой,
у каждого настраиваются ТИП: текст/число/ссылка и ОБЯЗАТЕЛЬНОСТЬ;
кейс «Курс: Выпускник 2025/26» закрывается сразу). Полный реестр
(любые колонки создаются админом, база = динамические поля) —
ЗАПЛАНИРОВАН на будущее при передаче сервиса другим организациям
(люди ≠ дядя, потребуются другие наборы полей). При полной версии —
отдельный дизайн-цикл с миграцией.

## Даты-диапазоны: визуально одно, под капотом два (2026-09-13)

Соревнование может идти несколько дней. Хранение: два поля
(date, date_to; date_to опционально, пусто = однодневное; колонка начала
при реализации не переименовывалась и называется `date`, а не date_from).
Ввод: одно гибридное поле — цифры, диапазон вида «25-27.06.2026» или
«30.01-01.02.2026» разбирается на пару; календарик для обеих границ.
Отображение компактное: совпадающие месяц/год — «25-27.06.2026»;
Фильтры периодов: запись показывается, если ХОТЯ БЫ ОДНА из её дат
(date ИЛИ date_to) попала в диапазон фильтра — решение владельца
2026-09-13. Отчётный срез «год» — по date. Экспорт — оба поля/
компактная строка.

## Конфликт-режим импорта: очередь на подтверждение (2026-09-13)

Нормальный импорт проходит как есть. Строки, НЕ являющиеся полным
дублем, но похожие на существующие (по настраиваемому ключу
дедупликации; пока ключ ФИО+дата+вид спорта+название) — попадают
в ОЧЕРЕДЬ ПОДТВЕРЖДЕНИЯ (не вставляются молча и не отклоняют импорт):
админ на странице очереди видит строку-кандидат рядом с похожей

## Student Identity v1, Phase 1: фундамент «Студентов» (2026-09-20)

Первый шаг к стабильной личности студента вместо `sha256(ФИО)`: таблица
`students` (карточка: актуальные ФИО/пол/институт/группа/курс + псевдонимы
ФИО в `student_aliases`) и зарезервированные nullable-колонки
`competitions.student_ref_id` / `users.student_ref_id`.

Границы Phase 1 (осознанные решения):

- **Ноль изменений легаси-поведения**: `competitions.student_id`
  (sha256 ФИО) остаётся единственным рабочим ключом — кабинет атлета,
  merge, импорт/дедупликация, отчёты и выгрузки работают как раньше;
- **Никаких авто-созданий и авто-связываний** карточек: строки `students`
  создаёт только admin (`/admin/people`); существующие записи и аккаунты
  НЕ мигрируются (`student_ref_id` всегда NULL);
- **`merged_into_id` зарезервирована** — не пишется и не читается;
- **Физического удаления студентов нет** — только деактивация
  (`active = 0`), как у значений справочников;
- дубликаты полного ФИО у разных карточек РАЗРЕШЕНЫ (тёзки — отдельный
  открытый вопрос, см. data-model.md);
- правка карточки меняет только актуальные данные: исторические записи
  не переписываются (для переноса записей — прежний merge).

## Student Identity v1, Phase 2: сопоставление данных (2026-09-20)

Заполнение стабильных связей `competitions.student_ref_id` /
`users.student_ref_id` по СУЩЕСТВУЮЩИМ записям и аккаунтам — вручную,
администратором (`/admin/people/reconcile`). Принцип фазы: **кандидаты —
предложения, решает админ**; ничего не связывается автоматически, привязка
меняет только `student_ref_id` (снимки в записях, легаси-ключ sha256(ФИО),
кабинет атлета, отчёты, импорт/экспорт, календарь и вложения связь не
читают — Phase 3 не начата).

Ключевые решения:

- **неактивные карточки недоступны для привязки** (`student_inactive`):
  сопоставление наводит порядок среди живых студентов, ошибка — явная
  с ФИО в тексте;
- **массовая привязка атомарна** («всё или ничего»): если хотя бы одна
  выбранная запись уже привязана, не меняется ничего — проверка и UPDATE
  под одной блокировкой хранилища;
- **одно audit-событие на массовую привязку** (`student_records_bulk_linked`
  со списком id), одиночная — `competition_linked_to_student`;
  `student_created` из сопоставления несёт `source` (`reconciliation-record`
  / `reconciliation-user`), Phase 1-создания — без него;
- **кандидаты — только точное совпадение** (strip + casefold, т.е. БЕЗ
  учёта регистра; сравнение в Python — lower() в SQLite не знает
  кириллицы) ФИО с `full_name` или псевдонимом АКТИВНОЙ карточки
  (совпадение по full_name приоритетнее псевдонима); неактивные карточки
  кандидатами не считаются, написания, отличающиеся не только регистром
  (ё/е, опечатки, инициалы) — тоже; размытые совпадения
  остаются будущим решением;
- **два аккаунта атлета МОГУТ указывать на одну карточку** (возможные
  дубликаты — вопрос модерации, не запрета): карточка студента показывает
  предупреждение при >1 аккаунте;
- **псевдонимы ФИО аккаунта НЕ копируются** в `student_aliases` при
  создании студента из профиля и не участвуют в кандидатах — они остаются
  механизмом кабинета атлета; псевдонимы карточки админ ведёт вручную;
- гонка при «создать студента из записи/профиля»: карточка создаётся и
  остаётся, привязка в гонке проигрывает с понятным flash-сообщением,
  источник не трогается.

## Student Identity v1, Phase 2.5: импорт студентов из Excel (2026-09-20)

Загрузка списка студентов `.xlsx` с предпросмотром и построчным
подтверждением (`/admin/people/import`, admin-only). Принцип фазы:
**предпросмотр не пишет в БД ничего, кандидаты — только предложения,
решает админ**. Точное совпадение ФИО с существующей карточкой никогда не
создаёт, не объединяет и не связывает ничего автоматически. Импорт трогает
ТОЛЬКО `students` + `audit_log`: записи соревнований, аккаунты и
`student_ref_id` не меняются, справочники только читаются (подсказки
института/группы), в `catalog_values`/`levels` импорт студентов не сеет
НИЧЕГО — в отличие от импорта записей, где справочник пополняется из
вставленных строк.

Ключевые решения:

- **staging в памяти, а не в БД** (прецедент `login_failures`): словарь
  процесса `student_import_sessions`, токен `secrets.token_urlsafe(16)`,
  TTL 2 часа, одна сессия на админа (новая загрузка заменяет прежнюю).
  Приложение однопроцессное (один worker Sanic), поэтому словарь процесса
  — корректное хранилище; рестарт теряет сессии без последствий — админ
  просто загружает файл заново, БД не затронута. Таблицу под одноразовые
  данные не заводим;
- **всё производное пересчитывается при каждом рендере** (кандидаты,
  подсказки справочников, группы дублей ФИО, категории, счётчики) — в
  сессии хранятся строки файла, решения по ним и фиксируемый рендером
  признак `had_candidates`, поэтому правка ФИО строки естественно
  переводит её между категориями «новые»/«требуют решения»;
- **массовое создание атомарно и с повторной проверкой**: «Создать N
  новых» вставляет ВСЕ чистые строки одной транзакцией
  (`create_students`, «либо все, либо ничего»). В батч входят только
  строки без кандидатов на момент рендера предпросмотра (признак
  `had_candidates`): неразобранные строки с кандидатами в батч НЕ входят
  и отмену не вызывают — их решает админ по отдельности. Полная отмена
  («Ничего не создано…») срабатывает, только если у ранее чистой строки
  совпадения ПОЯВИЛИСЬ между рендером и кликом (строки
  переквалифицируются в «требуют решения» при следующем рендере).
  Одиночное «Создать» при 100% совпадении разрешено — полные тёзки
  бывают; переспрашивать кандидатов не нужно, кнопку нажали осознанно;
- **«использовать существующего» не пишет ничего**: пометка только в
  сессии предпросмотра — никаких связей записей/аккаунтов не создаётся
  (это отдельный ручной workflow сопоставления, Phase 2);
- **справочники — только чтение**: институт автозаполняется по группе,
  если она принадлежит ровно одному институту; созданной карточке
  достаётся ровно показанное в предпросмотре значение (канонизация
  регистра, автозаполнение с бейджем «определён по группе»); неизвестная/
  неоднозначная группа и «группа относится к другому институту» —
  предупреждения без изменения значений;
- **ошибочные строки не молчат и не чинятся сами**: недопустимый Пол
  («М»/«Ж»/пусто) и пустое ФИО — строка уходит в «Ошибочные» с причиной;
  правка (ФИО редактируемо — в отличие от очереди конфликтов импорта
  записей) или «Пропустить». Завершению импорта ошибочные строки НЕ
  мешают — блокируют только неразобранные, итоговое событие несёт
  `errors`;
- **дубли ФИО в файле** (casefold(strip)) помечаются всем членам группы
  «Одинаковые ФИО в файле: строки N, M» и переводятся в «требуют
  решения»; создать обе явно можно — тёзки;
- **аудит**: `student_created` с `source: excel-import` на каждую
  созданную карточку, один `student_import_completed`
  `{created, reused_existing, skipped, errors, total}` при завершении;
  «Отменить импорт» — без аудита, созданные подтверждением карточки
  сохраняются (создание было явным действием);
- значения файла — недоверенный ввод: шаблоны рендерят их только через
  Jinja-экранирование, confirm-строки кнопок содержат только числа.

## Перенос группы в другой институт (2026-09-22)

Админское действие `/admin/catalogs/group/<id>/move` (шаг 1 — выбор
целевого института в списке групп, шаг 2 — страница-подтверждение со
счётчиками и обязательной галочкой, без JS). Чинит ошибочную привязку
группы к институту.

- **почему карточки студентов обновляются — в отличие от переименования**.
  Переименование (2026-09-13) меняет только текст значения и по галочке
  переписывает записи: там правится «написание», историчность записей —
  осознанный выбор. Перенос группы — починка неверной привязки: карточка
  студента хранит АКТУАЛЬНЫЕ данные и обязана совпадать со справочником,
  поэтому `students.institute` обновляется всегда (вместе с `updated_at`),
  без опции «не трогать». Записи соревнований обновляются так же, как при
  переименовании с «обновить записи»;
- **семантика отбора — точная пара строк** `(institute, group)` в
  `competitions` и `(institute, group_name)` в `students` — как у
  переименования и `count_records_using`: одноимённые группы других
  институтов и строки без института не затрагиваются;
- **одна транзакция** в `move_catalog_group`: справочник (`parent_id`) +
  записи + карточки; любая ошибка — откат, ничего не меняется;
- **конфликт**: в целевом институте уже есть группа с таким именем
  (без учёта регистра, уникальность — по паре родитель+значение) — отказ с
  подсказкой сначала переименовать одну из групп; перенос «в тот же
  институт» и неизвестные id — тоже отказ. Скрытая группа переносима:
  активность — видимость в подсказках, не запрет действий;
- **аудит**: `catalog_group_moved` `{group, old_institute, new_institute,
  students_updated, competitions_updated, group_id}`.

## Файл положения события календаря (2026-09-22)

Один файл «положения о соревновании» на событие календаря — регламент
соревнования рядом с событием, на которое ссылаются участники.

- **хранение**: колонки `calendar_events.regulation_filename` (исходное
  имя для скачивания) и `regulation_stored_name` (служебное имя файла на
  диске); обе NULL = файла нет. Файл лежит в
  `data/files/calendar/<event_id>/<uuid4>.<ext>` — общий корень
  `data/files` с вложениями, поэтому существующие бэкапы (zip всего
  `data/files`) покрывают положения без изменений;
- **валидация — как у вложений**: PDF/JPEG/PNG, до 5 МБ, проверка и
  расширения, и сигнатуры (`ATTACHMENT_*` / `detect_attachment_type`);
  исходное имя очищается от пути (`rsplit('/')`), путь на диске — только
  служебный `uuid4`;
- **жизненный цикл**: загрузка/замена — новый файл на диск, затем колонки
  БД, затем best-effort удаление прежнего файла; удаление положения —
  колонки в NULL + удаление каталога; удаление события — каталог
  положения удаляется вместе с событием. Подсказка `url` события остаётся
  отдельным полем (ссылка на внешний сайт), файл — не замена ей;
- **права**: скачивание — все аутентифицированные не-атлеты (как страница
  события); загрузка/замена/удаление — модераторы (admin/editor);
- **аудит**: `calendar_regulation_uploaded` `{event_id, event_name,
  filename, replaced}` и `calendar_regulation_deleted` `{event_id,
  event_name, filename}`.

## Полное удаление карточки студента (2026-09-24)

Admin-only hard delete ошибочно созданной карточки — только со страницы
карточки (`POST /admin/people/<id>/delete`), с транзакцией и аудитом.

- **блокеры — любые связи**: записи (`competitions.student_ref_id`),
  аккаунты (`users.student_ref_id`; счётчик без фильтра роли — `link_user` /
  `relink_user` пишут только athlete, но прямые/легаси строки накрываются
  тем же запретом) и карточки, слитые в эту (`students.merged_into_id`).
  При любом блокере не меняется ни одна строка; сообщение показывает
  фактические счётчики только ненулевых блокеров;
- **одна транзакция «либо всё, либо ничего»**: удаление псевдонимов
  (`student_aliases`) + самой карточки (`students`); сбой на любом шаге —
  полный откат. Записи соревнований и аккаунты вместе с карточкой НЕ
  удаляются — их отвязывают отдельно до удаления;
- **аудит**: успех — `student_deleted` `{student_id, full_name}` (ФИО
  берётся снимком до удаления); заблокированная попытка в аудит не
  пишется (конвенция остальных отказов);
- **неактивная карточка без связей удаляется так же** — `active` скрывает
  карточку из поиска/импорта, но не является связью;
- для используемых карточек остаётся деактивация; bulk-удаления, удаление
  из списков/поиска и автопоиск кандидатов на удаление НЕ добавлялись.

## Event Model, Wave 1 P0/P1: схема и проводка participation-identity (2026-09-24)

Фундамент целевой архитектуры «событие → участие» без изменения
пользовательского поведения: колонки существуют и проводятся через
storage, runtime их не читает.

- **состав колонок `competitions`** (P0): `discipline TEXT NULL`,
  `result TEXT NULL`, `calendar_event_id INTEGER NULL` — аддитивные
  ALTER'ы, существующие строки NULL. Participation-identity будущих фаз =
  (`calendar_event_id`, `student_ref_id`, `discipline`);
- **`app_settings`** (P0): `key TEXT PRIMARY KEY, value TEXT NOT NULL` —
  флаги миграций. Засеян `identity_mode='dual'` (подготовка Phase 3
  dual-read); читателей флага в этой волне НЕТ — seed существует, но
  ничего не переключает (с Phase 3 флаг читается, см. следующий раздел
  Phase 3);
- **индексы** (P0): `idx_competitions_calendar_event_id`,
  `idx_competitions_student_ref_id` — обычные, не UNIQUE: уникальность
  связи управляется приложением;
- **backfill `calendar_event_id`** (P0): при каждом старте, тем же
  предиктом, что подсчёт участников события (`name + date +
  COALESCE(date_to, '')`). Правила: unique-only (линкуются только NULL-
  строки с ровно одним совпадением), no-guess (0 или >1 совпадений —
  остаётся NULL), already-linked не меняются. Естественная
  идемпотентность: повторные старты линкуют только newly-unique NULL-
  строки; счётчики — одна INFO-строка только при наличии NULL-строк;
- **проводка (P1)**: `discipline`/`result`/`calendar_event_id` пишутся
  INSERT'ом из модели (None → NULL), читаются общим SELECT и
  `_row_to_competition`; `update_competition` правит только
  `discipline`/`result` — `calendar_event_id` в SET НЕ входит (ссылка на
  событие — управляемое поле будущих link/unlink P2, общий update её
  сохраняет). Экспорт в Excel поля не отдаёт — контракт выгрузок
  не меняется; payload очереди конфликтов сериализует поля как None,
  легаси-payload без ключей валидируется (дефолт None).

## Event Model, Wave 1 P2: стабильная связь «запись → событие» (2026-09-25)

`calendar_event_id` становится primary-ключом принадлежности участвия
событию; пресет перестаёт быть идентификатором состава. Схема не менялась
(колонка с P0), backfill не трогался.

- **id-first чтение (решение A)**: список участников события
  (`list_calendar_event_participants`) и счётчики `/calendar`
  (`list_calendar_events`) — по `calendar_event_id` (LEFT JOIN по ссылке),
  БЕЗ preset-fallback: NULL-legacy-строка, совпавшая с пресетом по
  случайности, на странице события не показывается и в счётчики не входит;
- **блокировщик удаления — консервативный OR (решение A, выбор владельца)**:
  `count_calendar_event_participants` считает записи по ссылке ИЛИ по
  пресету. Осознанный over-block: удалить событие, у которого остались
  записи-двойники пресета, молча хуже, чем один раз отказать и разобрать
  случай вручную;
- **вставки пишут ссылку**: ручное добавление участника
  (`POST /calendar/<id>/participants`) и все три пути импорта участников
  (row-add / create-student / bulk-commit) ставят
  `competition.calendar_event_id = event.id` до вставки — новые участия
  связаны всегда;
- **edit-sync одной транзакцией**: `update_calendar_event` под `_lock`
  (паттерн `import_competitions`: try / commit / except BaseException
  rollback) обновляет `calendar_events`, затем `UPDATE competitions SET
  name/date/date_to/sport/level WHERE calendar_event_id = ?` и возвращает
  synced = rowcount. Состав синхронизации — ровно 5 event-owned полей;
  student-поля/место/discipline/result/extra_data не затрагиваются;

## Student Identity v1, Phase 3: runtime-идентичность кабинета атлета (2026-09-25)

Runtime кабинета атлета и права атлета начинают читать стабильные связи
`student_ref_id` (Phase 1/2); переключение режимов — рантайм-флагом
`app_settings.identity_mode`. Схема НЕ менялась: ни новых таблиц, ни
колонок, ни backfill — используются связи, накопленные сопоставлением и
импортами, и seed Wave 1 P0.

- **режимы dual/ref**: `'dual'` (по умолчанию и на проде) — видимость
  `owner OR student_ref_id OR легаси-хеш sha256(ФИО)`; `'ref'` — только
  `owner OR student_ref_id`. Флаг читается НА КАЖДЫЙ запрос без кэша
  (`get_identity_mode`); нет строки или неизвестное значение → `'dual'`:
  легаси-поведение безопаснее (ref мог бы скрыть записи из кабинета);
- **один источник scope**: `_competition_scope_clauses(ref, режим)` —
  список главной, счётчик страниц и `has_unapproved` согласованы (одни и
  те же параметры); `athlete_identity_context` собирает scope запроса
  (id аккаунта, student_ref_id, хеши ФИО) в одном месте;
- **права writes: owner OR ref в обоих режимах; хеш-ветка прав — только
  в dual** (исправление по QA D2): `user_owns_record` получает ветку
  `student_ref_id` (правка записи, вложения) поверх owner; легаси-хеш
  ФИО даёт право на запись только в dual-режиме. В ref хеш-ветка прав
  отключена: разрешённый flip (H=0) означает, что хеш-совпадения уже
  покрыты owner/ref, поэтому она не даёт ничего легитимного и лишь
  открывала бы тёзкам правку чужих записей и доступ к чужим вложениям
  на post-flip данных;
- **flip с guard'ом без waiver**: переход dual→ref блокируется, пока
  счётчик H (записи, видимые атлетам ТОЛЬКО по хешу: хеш совпал, но не
  owner и не по связи) ≥ 1; H≥1 — формы нет, подделанный POST отклоняется
  flash-сообщением, режим прежний, аудит НЕ пишется; H=0 — форма с
  подтверждением «кабинеты не изменятся»; ref→dual — всегда. Проверка H и
  UPDATE атомарны под блокировкой storage (`set_identity_mode_guarded`).
  Успех — аудит `identity_mode_changed` `{old, new, hash_only_visible}`;
- **отчёт проверки** (третья вкладка `/admin/people/reconcile/identity`):
  per-user ветки owner/ref/hash, «пропадёт» (hash-only), «риск тёзки»
  (запись совпала по ФИО, но связана с ДРУГОЙ карточкой — легаси
  показывает тёзку в кабинете), первые 20 пропадающих записей, бейдж H на
  всех трёх вкладках раздела. Счётчик H per-user: одна запись, совпавшая
  с двумя аккаунтами, считается дважды — каждый кабинет её потеряет;
- **предпросмотры вместо сюрпризов**: карточка студента — «Видимо атлету:
  сейчас N / после отвязки M» с тремя вариантами подтверждения (не
  изменится / частично / пропадёт всё); сопоставление аккаунтов —
  «Сейчас видно: K», у кандидата «после привязки: N», в ref-режиме —
  подсказка под «Создать студента» (без карточки атлет видит только
  свои записи);
- **инвариант теста привязки переписан под dual**: своя по ФИО запись
  видима до и после привязки, ЧУЖАЯ запись появляется в кабинете после
  привязки её карточки к аккаунту — плановое поведение dual-read (старый
  инвариант «кабинет не меняется» относится к Phase 2 и устарел);
- **чего режим НЕ меняет**: отчёты, выгрузки Excel, merge, дедупликация

## Event Model, P5a: Registry Import/Export (2026-09-25)

Реестр начинает работать с дисциплиной участия: импорт читает опциональную
колонку «Дисциплина», полный ключ дубля учитывает дисциплину, выгрузка

несёт дисциплину кандидата (таблица, форма ручной правки, diff аудита).

- **Р1 — коллизия label кастомных полей** (на производственной базе активны
  кастомы «Дисциплина»/«Результат», коллизия с базовыми колонками только по
  label): коллидирующие кастомные поля исключаются из списков колонок
  выгрузки и шаблона (`select_export_custom_fields` /
  `select_template_custom_fields`, сравнение label strip+casefold).
  Определения полей и их значения в реестре/`extra_data` не трогаются.
  Шаблон исключает только коллизию с «Дисциплиной» — фиксированной колонки
  «Результат» в шаблоне нет, кастомное поле с таким label остаётся в
  шаблоне как обычно. Старые файлы с колонками «Дисциплина»/«Результат»
  продолжают писаться в соответствующие кастомы;
- **Р2 — оригинал хранится, нормализация только в ключе**: дисциплина
  сохраняется в записи как введено (двойные пробелы, регистр);
  `normalize_discipline_for_dedup` (схлопывание пробелов + casefold)
  применяется только внутри полного ключа дубля;
- **Р3 — место колонок**: в шаблоне импорта «Дисциплина» — опциональная
  фиксированная колонка сразу после базовых (после «Курса»), «Результата»
  в шаблоне нет; в выгрузке реестра фиксированные «Дисциплина»/«Результат»

- **Р5 — двойная запись «Дисциплина» из файла**: значение пишется и в

## Event Model, P4: Event Participant Import v3 (2026-09-25)

Импорт участников события начинает работать с дисциплиной и результатом
участия и получает строгий repeat-safe дедуп: повтор уже существующего
участия не создаётся — вместо дубля доступно restricted-обновление
места/результата. Схема не менялась (колонки `discipline`/`result` с P0),
миграций нет.

- **F′ — дисциплина/результат как фиксированные колонки файла участников**:
  «Дисциплина» и «Результат» — опциональные колонки после «Места» в
  шаблоне, разборе, правке строки и таблице предпросмотра. Коллидирующие
  по label (strip+casefold) КАСТОМНЫЕ поля исключаются из ЭТОГО workflow
  (расширение P5a-exception; `select_template_custom_fields` реестра не
  трогается) — колонка файла одна. Дисциплина идёт в запись через
  `record['Дисциплина']` → `build_competition` (тот же путь, что у
  реестра, P5a-контракт не меняется), результат — присваиванием
  `competition.result` ПОСЛЕ build (базовый `result` импортом РЕЕСТРА
  по-прежнему не пишется; участия — другой workflow). Двойной записи в
  `extra_data` у участий НЕТ: источник — базовые колонки;
- **v2-правила классификации повторов** (пересчёт на каждом рендере;
  нормализация текстов strip+casefold, дисциплины —
  `normalize_discipline_for_dedup`, 0/пустое место-курс = «нет значения»;
  существующие участия читаются с legacy-фолбэком `discipline`/`result`
  NULL → `extra_data` активного кастома с тем же label, только чтение):
  - MATCHED (карточка строки определена): identity =
    (`calendar_event_id`, `student_ref_id`, нормализованная дисциплина).
    Совпадения нет → готова; есть и место+результат равны → «уже
    существует» (производный статус без действий, в БД ничего); отличаются
    → update-candidate с диффом место/результат (старое→новое, «—» для
    пустых) — построчные «Обновить существующее»/«Оставить существующее»;
  - CARDLESS (без карточки): контент-ключ = (`event`, нормализованное
    ФИО, нормализованная дисциплина), контент =
    пол/институт/группа/курс/место/результат/custom. Точная копия
    контента существующего участия → «уже существует»; ключ совпал,
    контент другой → «возможный дубль»: «Пропустить (default)» /
    «Добавить как новое». Обновить cardless-участие из импорта НЕЛЬЗЯ —
    кнопок и роута нет (обновление требует стабильной связи с карточкой);
    вставки cardless-строк всегда `student_ref_id IS NULL`;
  - повторы в файле: точная копия строки → производный «дубликат в файле
    — пропускается» (якорь — первая строка группы по номеру; флаг НЕ
    sticky — разобранный якорь продвигает следующую копию; в bulk не
    входит, завершение не блокирует; сервер обе не вставляет). Тот же
    ключ уникальности при РАЗНОМ контенте — взаимный конфликт строк
    (v2-семантика «требуют решения», пока одна не разобрана). Полного
    равенства мест/дисциплин достаточно для корректных мульти-дисциплин
    (100 м/200 м/эстафета одного человека — три участия);
- **серверный enforcement**: все пути вставки (row-add, create-student,
  bulk-commit) идут через `apply_event_participation_batch` — под `_lock`
  одной транзакции повторная проверка против живой БД и самого батча
  (intra-batch first-wins): MATCHED — identity (карточка+дисциплина),
  CARDLESS против живой БД — точный контент (то же ключ+другой контент —
  законное «добавить как новое»), внутри батча — контент-ключ
  (ФИО+дисциплина: обе строки одного файла с тем же ключом не вставляются);
  вставки + синхронизация справочников + один COMMIT; коллизия — откат
  всего батча (паттерн `import_competitions`) и flash. Одиночные добавления
  дополнительно проходят guard повторной классификации. Состав ключей
  нормализуется ЕДИНОЙ реализацией storage (`participation_content_key` и
  соотв. хелперы) — предпросмотр и сервер сравнивают символ в символ;
- **обновление существующих — вне edit-path записи**: «Обновить
  существующее» выполняет restricted-UPDATE
  (`update_event_participation_result`: SET только `position`/`result`,
  WHERE `id + calendar_event_id`) — снимок участника, custom-поля,
  вложения, `student_ref_id` и связь с событием физически недостижимы;
  аудит `event_participant_updated` `{event_id, record_id,
  position/result как {old, new}}`. Общий `/competition/<id>` (O1) и
  edit-sync события (P2) по-прежнему сохраняют `discipline`/`result`;
- **MATCHED-C вне bulk**: update-candidate-строки в массовый батч НЕ
  входят — только построчные решения (bulk-батч «обновляющего» сегмента
  нет, текст кнопки прежний); confirm-текст bulk дополнительно называет
  числа непопадающих «уже существует»/«дубликатов в файле». Счётчики
  сессии/аудита `event_participants_import_completed` расширены:
  `added / updated / kept / already_exists / file_duplicates / errors /
  total`; завершение блокируют только строки, требующие решения.

## Event Model, P5b: явное связывание «запись → событие» (2026-09-25)

NULL-запись реестра можно явно связать с событием календаря: страница
`/competition/<id>/link-event` (иконка-звено в строке реестра, admin/editor)
с GET-поиском событий, пресет-кандидатами и диффом «после связывания», либо
созданием нового события прямо со страницы записи. Массовый разбор
legacy-остатков — «Обслуживание базы → Связывание с календарём» (admin).

- **guarded UPDATE вместо SELECT-then-UPDATE без защиты**: и одиночное
  связывание (`link_participation_to_event`), и create+link
  (`create_calendar_event_and_link`), и пакет (`apply_calendar_link_backfill`)
  пишут ссылку UPDATE `... WHERE id = ? AND calendar_event_id IS NULL`.
  Гонку «двое связывают одну запись» закрывает rowcount: 0 → откат
  (одиночный путь) / пропуск строки (пакет), существующая ссылка и поля
  записи не перезаписываются. Проверки «запись существует / ещё NULL» в
  create+link выполняются ДО вставки события — сбой не оставляет
  событий-сирот;
- **связывание = ссылка + синхронизация снимка**: в запись копируются те же
  5 event-owned полей (name/date/date_to/sport/level), что переносит
  edit-sync P2 (`update_calendar_event`) — после связывания запись и событие
  согласованы сразу, без обязательной правки события. Участие-поля (ФИО,
  институт, группа, курс, место, дисциплина, результат, custom) не
  затрагиваются. Дифф до связывания (включая warning «поле очистится»,
  когда у события поле пусто) показывается и на странице записи, и в
  предпросмотре пакета — очистка никогда не происходит молча;
- **пакет = matched + sync, ambiguous — никогда**: предикат предпросмотра
  и apply — ровно семантика стартового P0-backfill'а
  (`_calendar_preset_match_sql`: name + date + COALESCE(date_to, '')).
  Автоматически линкуются только строки с ровно одним кандидатом;
  неоднозначные остаются на ручное связывание со страницы записи
  (no-guess, как у P0). Кнопка пакета требует явного confirm с числом
  записей и перечнем очисток;
- **взаимодействие со стартовым P0-backfill**: backfill при каждом старте
  по-прежнему проставляет только ссылки однозначным пресетам, поля записи
  не синхронизирует; batch-apply — то же условие плюс синхронизация 5 полей.
  Двойной прогон невозможен (guard `IS NULL` в обоих); строка, связанная
  вручную между предпросмотром и apply, пропускается как skipped — пакет
  не валится и чужую ссылку не трогает;
- **создание события со страницы записи**: форма — та же, что у
  `/calendar/new` (период, валидация `parse_calendar_event_form`, только
  http/https-ссылки), предзаполнена снимком записи; INSERT события +
  guarded UPDATE записи одной транзакцией. Аудит: `calendar_event_created`
  (`source: 'registry'`) + `participation_linked` (`event_created: true`);
  создание события из самого календаря по-прежнему не аудируется;
- **права**: страница и оба POST-связывания — модераторы (admin/editor,
  как событие и его правка); массовое связывание — только admin (действие
  «Обслуживания базы»). Viewer/athlete: 403, иконки связи в реестре нет.
