# Решения по модели данных

## Смена группы/института/курса студентом

Запись о соревновании — **исторический факт участия**. Группа, институт и курс
в записи отражают то, чем студент был на момент соревнования, и при смене
профиля **не перезаписываются**: в 2024 он выступал за ПГС-101 — так это и
останется в записи и в отчётах за 2024 год.

Текущие значения (ФИО, пол, институт, группа, курс) хранятся в профиле
пользователя (`users.profile_data`) и:

- автоподставляются в новые записи атлета, когда поле не заполнено в форме;
- поле формы всегда имеет приоритет над профилем;
- профиль редактирует сам пользователь (для атлетов — страница «Профиль»).

Отчёт «количество участий» группирует по данным записи, поэтому участие за
разные годы с разными группами попадает в разные строки — это осознанное
поведение: отчёт показывает факты на дату.

Если однажды понадобится массовая правка (например, «привести все записи
студента к текущей группе») — это отдельный админский инструмент с явным
подтверждением, не автоматика.

## Личность и смена фамилии

Якорь личности — аккаунт. У аккаунта есть список ФИО-псевдонимов
(`users.name_aliases`):

- каждое ФИО из профиля автоматически дописывается в псевдонимы (список
  только растёт), поэтому смена фамилии ничего не отрывает;
- админ может привязать дополнительное ФИО к аккаунту вручную
  (`POST /admin/users/<id>/alias`) — для истории, заведённой под старой
  фамилией до создания аккаунта;
- кабинет атлета = свои записи + записи с `student_id` из хешей любых
  его псевдонимов.

Отчёт «количество участий» группируется по данным записи (student_id +
ФИО + группа + курс — исторические факты). Чтобы смена фамилии не
дробила человека в цифрах, есть админский merge
(`POST /admin/students/merge`): превью показывает, сколько записей
будет объединено; подтверждение переписывает `student_id` старого ФИО на
новое; по умолчанию перезаписывается и отображаемое ФИО записей
(галочка «оставить исторические» отключает). Merge не автоматизируется:
однофамильцы-тёзки существуют, решение остаётся за админом.

## Привязка существующих записей к новому аккаунту атлета

Кейс: админ заранее внёс участия человека, потом человеку создали аккаунт
атлета. Связь не требует отдельной кнопки «забрать записи»:

- кабинет атлета показывает записи `owner_id = <атлет>` **или**
  `student_id = sha256(ФИО из профиля)`;
- при пустом ФИО в профиле атлет видит только собственные записи;
- правила правок при этом не меняются: правка атлета (включая «свою по
  ФИО» запись, созданную админом) отправляет запись на повторную проверку;
  правка модератора — подтверждает. Решение по роли, а не по владельцу;
- при смене ФИО в профиле состав «подтянутых» записок меняется вместе с ним.

## Подсказка ФИО и приватность (2026-09-12)

Полный список ФИО из записей (`GET /api/students`) доступен только
admin/editor — оператору он и так виден в таблице. Атлету список чужих
ФИО не отдаётся: только точечная проверка своего ФИО
(`GET /api/students/lookup?name=` → `found` true/false), чтобы атлет
не мог перебором узнать участников. Подсказки-список (datalist) — только
в админских формах (merge-секция, привязка псевдонима); в профиле атлета —
текстовая строка «найдено/не найдено» без раскрытия чужих данных.

## Тёзки (одинаковые ФИО у разных людей)

Принято: не обрабатывать заранее. Влияние ограничено: в отчёте тёзки и так
склеены (исторически так было с группировкой по ФИО); в кабинете тёзка-атлет
увидит записи двойника (просмотр, не порча); правка «своей по хешу» записи
тезки уходит на модерацию, модератор — страховка. При реальном случае
(жалоба «в кабинете чужая запись») — точечно: снять лишний псевдоним или
усложнить привязку подтверждением админа.

## Аудит-журнал безопасности (2026-09-12)

Новая таблица `audit_log` (append-only, записи только добавляются, не
редактируются и не удаляются из UI): `id, created_at, user_id, username,
action, details`. Фиксируемые события (минимальный набор):

- `login_success` / `login_failed` — входы (username при неудаче пишем,
  user_id может быть пустым);
- `password_changed` — смена пароля (кем и чьего аккаунта);
- `record_approved` / `record_rejected` — решения модерации с комментарием;
- `students_merged` — merge с параметрами (from_name, to_name, счётчик,
  rewrite_names);
- `alias_added` — привязка ФИО к аккаунту администратором.

Просмотр — страница `/admin/audit`, только admin, последние записи сверху,
без редактирования. Журнал — инструмент разбора инцидентов, не база для
отчётов: без пагинации на первом шаге (см. пункт 4 бэклога про триггер
объёма). Решения по роли/статусу записей в журнал не пишутся точечно —
их покрывают `record_approved`/`record_rejected` при явном ревью, а правка
с авто-подтверждением модератора фиксируется как `record_approved`.

## Merge и псевдонимы (2026-09-12, по наблюдению QA)

QA-прогон выявил: `merge` с `rewrite_names` переписывал `student_id` записей
на хеш нового ФИО, но не трогал `users.name_aliases` — записи выпадали из
кабинета атлета, пока админ вручную не привяжет новое ФИО. Признано багом,
а не задуманным поведением: кабинет должен переживать merge без ручной
перевязки.

Решение: при выполнении `POST /admin/students/merge` автоматически
дописывать `to_name` в `name_aliases` каждого аккаунта, у которого среди
псевдонимов есть `from_name` (принцип «список псевдонимов только растёт»
не нарушается — ничего не удаляется). `from_name` из псевдонимов НЕ
удаляется: старое ФИО остаётся в истории аккаунта. Обратная ситуация
(записи, созданные под новым ФИО до merge) не меняется. Тест: merge
`from_name`→`to_name` при аккаунте с псевдонимом `from_name` — после
слияния записи видны в кабинете атлета.

## Хранение и схема: SQLite остаёмся, базовые поля не расхардкоживаем (2026-09-12)

Обсуждался переезд с SQLite и перевод базовых полей записи (ФИО, пол,
институт, группа, курс, вид спорта, дата, уровень, название, место) в
управляемую схему. Решение:

- **SQLite остаётся.** Один инстанс на организацию, один оператор, объём
  — тысячи записей в год; WAL уже включён. Переезд на серверную СУБД даёт
  ноль продуктовой ценности сейчас и стоит: деплой-сложность (сервис,
  бэкапы, миграции), переписывание storage-слоя, двойные тесты. Триггеры
  для пересмотра — те же, что у пагинации (п.4 бэклога): реальный рост
  нагрузки или несколько воркеров с общей БД.
- **Базовые поля остаются в коде.** Расхардкод = единый реестр полей поверх
  существующих кастомных: затрагивает build_competition, импорт/экспорт
  xlsx, отчёты, автоподстановку из профиля, все шаблоны и 99 тестов —
  это дорогая переработка с высоким регресс-риском ради гипотетической
  пользы. Домен стабилен: эти поля одинаковы у любого вуза. Потребность
  «ещё поле» закрывается кастомными полями (label, тип, обязательность,
  показ в таблице/экспорте). Управление **значениями**-справочниками
  (уровни, виды спорта, институты) — отдельная дешёвая задача (п.12
  бэклога), её делаем. К реестру полей вернуться — только если появится
  вторая организация с другой базовой структурой.

## Очистка и выгрузка базы (2026-09-12)

Очистка — только admin, в два шага: выбор объёма + ввод подтверждающей
фразы в поле (не confirm()). Варианты очистки по возрастанию ущерба: 1) только вложения,
2) только записи, 3) записи + вложения («всё»). Дополнительно — очистка
по дате: «записи с датой соревнования ДО указанной» (решение
2026-09-13: критерий — дата соревнования, а не дата создания записи),
с галочкой «вместе с их вложениями» (по умолчанию включена).

Перед любой очисткой автоматически создаётся архив удаляемого
(решение 2026-09-13): xlsx удаляемых записей (все колонки, как экспорт)
+ zip их вложений; лежит в data/backups, скачивается со страницы
обслуживания. Это страховка от «очистил и пожалел» — отдельно от
штатных бэкапов по таймеру. Пользователей, кастомные поля,
справочники и сам журнал аудита очистка не трогает; каждое выполнение
пишется в аудит с параметрами. Выгрузка базы — xlsx «всё в одном файле
по листам» (записи, пользователи+псевдонимы, справочники) + существующие
выгрузки остаются.

## Справочники значений (2026-09-12)

Управляем админом — значения, не схема. Принципы:

- Записи остаются свободным текстом (историчность): справочник НЕ
  валидирует и не перезаписывает значения в существующих записях.
- Справочники «Виды спорта» и «Институты» ведут себя как уровни сегодня:
  новое значение из записи/импорта автоматически попадает в справочник;
  админ может скрыть значение (скрытое не показывается в подсказках форм,
  но остаётся в записях и отчётах) или добавить значение руками.
- Назначение — подсказки (datalist) в формах и порядок в списках, не
  контроль. Место — страница «Справочники» в админке; уровни переезжают
  туда же из /admin/levels (старый URL остаётся рабочим).

## Удаление пользователей (2026-09-12)

`POST /admin/users/<id>/delete`, только admin. Семантика:

- Записи — исторические факты: при удалении аккаунта НЕ удаляются,
  `owner_id` обнуляется; запись остаётся в таблице, отчётах и выгрузках.
- Псевдонимы ФИО и привязка кабинета исчезают вместе с аккаунтом
  (ожидаемо: якорь личности удалён).
- Журнал аудита не трогается (append-only; события хранят username
  текстом и переживают удаление).
- Блокировки: нельзя удалить себя; нельзя удалить последнего активного
  админа. Подтверждение — ввод логина в поле (как wipe с фразой).
- Каждое удаление — audit-событие `user_deleted` (кто, кого, сколько
  записей отвязано).

Автогенерация паролей — UI-фича формы (криптослучайная строка без
двусмысленных символов, показ один раз с копированием), серверных
изменений не требует.
