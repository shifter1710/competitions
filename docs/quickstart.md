# Быстрый старт

Два сценария: **(А)** новая раскатка пустого инстанса и **(Б)** перенос
работающего инстанса на другой сервер. Всё, что описано, соответствует
файлам репозитория (`docker-compose.yml`, `Dockerfile`, `deploy/`,
`scripts/`); пути в юнитах под свой сервер нужно подставить свои.

Продовая схема: контейнер приложения слушает `127.0.0.1:8081`, наружу его
отдаёт nginx по HTTPS. Вся живая информация — база SQLite и вложения —
лежит в каталоге `data/` репозитория.

## Требования

- Сервер с Docker и плагином `docker compose` (проверка:
  `docker compose version`).
- nginx (TLS-терминация и проксирование); для сертификата — certbot/Let's
  Encrypt или свой сертификат.
- systemd — для автостарта контейнера и бэкап-таймера (опционально, но
  рекомендуется).
- Для бэкап-скрипта достаточно системного `python3` (только стандартная
  библиотека).
- Альтернатива без Docker: Python 3.10+, `pip install -r requirements.txt`,
  запуск `sanic src.main:app` — как в [README](../README.md); дальше по
  тексту всё то же, кроме compose-команд.

## Сценарий А. Новая раскатка

### 1. Клонировать репозиторий

```bash
git clone <адрес-репозитория> competitions
cd competitions
```

### 2. Подготовить `.env`

```bash
cp .env.example .env
```

Минимум в `.env`:

- `AUTH_SECRET_KEY` — случайная строка, например
  `python3 -c "import secrets; print(secrets.token_hex(32))"`.
  С «слабыми» значениями приложение откажется стартовать.
- `AUTH_ADMIN_USERNAME` / `AUTH_ADMIN_PASSWORD` — учётка администратора
  (создаётся при первом старте). Пароль — сильный и уникальный: со
  значением-заглушкой из `.env.example` (`change-me*`) первый старт
  завершится ошибкой с именем переменной.
- `AUTH_EDITOR_USERNAME` / `AUTH_EDITOR_PASSWORD` — учётка оператора;
  требование к паролю то же.
- `AUTH_VIEWER_*` — опционально; пустые значения = учётка не создаётся
  (если задаёте — пароль тоже должен быть сильным).

Важно: `AUTH_*`-пароли используются только при первом старте для посева
учёток. Дальше пароли меняются в интерфейсе («Админ → Пользователи»),
правка `.env` задним числом на существующие учётки не влияет.
Полный список переменных — в [README](../README.md).

### 3. Собрать и запустить контейнер

```bash
docker compose up -d --build
```

Что произойдёт (по `docker-compose.yml` и `Dockerfile`):

- образ собирается из `Dockerfile` (python:3.10-slim + зависимости из
  `requirements.txt`);
- контейнер публикуется на `127.0.0.1:8081` (наружу напрямую не торчит);
- каталог `./data` монтируется в контейнер — база и вложения переживают
  пересборки;
- healthcheck пингует `/healthcheck` каждые 30 секунд.

Проверка на сервере: `curl http://127.0.0.1:8081/healthcheck` → `OK`.
При первом старте создаются `data/competitions.sqlite3`, стартовые уровни
(«внутривузовские», «межвузовские») и учётки из `.env`.

### 4. nginx и сертификат

Основа — [deploy/nginx/competitions.conf](../deploy/nginx/competitions.conf).
Скопируйте его в конфигурацию nginx (например, в
`/etc/nginx/sites-available/` + симлинк в `sites-enabled/` — по правилам
вашего дистрибутива) и поправьте:

- `server_name` — ваш домен или IP (в шаблоне прописан домен прод-инстанса
  и его IP-вариант);
- пути к сертификату и ключу (шаблон рассчитан на certbot: файлы в
  `/etc/letsencrypt/live/<домен>/` и два `include` из
  `/etc/letsencrypt/`);
- обязательно сохраните `client_max_body_size 8m;` — лимит вложений в
  приложении 5 МБ, а дефолт nginx (1 МБ) резал бы загрузку вложений с
  ошибкой 413 до того, как запрос дойдёт до приложения;
- `proxy_read_timeout 120s` оставьте как есть.

В шаблоне есть редирект HTTP → HTTPS. После правок:
`nginx -t && systemctl reload nginx`.

Опционально — автостарт контейнера при перезагрузке:
[deploy/systemd/competitions-compose.service](../deploy/systemd/competitions-compose.service).
Поправьте в нём `WorkingDirectory` на путь к репозиторию, затем:

```bash
cp deploy/systemd/competitions-compose.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now competitions-compose
```

### 5. Подключить backup и независимые проверки

[scripts/backup_sqlite.py](../scripts/backup_sqlite.py) использует SQLite backup
API (включая WAL), создаёт gzip, ZIP всех вложений и manifest. Комплект публикуется
в `data/backups/sqlite/sets/<id>/` только после проверки gzip, SQLite
`quick_check`, ZIP CRC, SHA256 и наличия файлов, на которые ссылается снимок БД.
Повторная проверка изменений снижает риск несогласованности, но не является
атомарным снимком БД и файловой системы.

Ротация в этом пакете **не выполняется**; `--keep 14` не удаляет копии.
Старые архивы остаются на месте. Планирование retention — отдельная задача.

Подключайте daily и offsite units согласованно: прежний скрипт, отправляющий
только файлы из корня каталога, не увидит новый формат `sets/<id>/`.
Шаблоны `competitions-backup.*`, `competitions-backup-offsite.*` и
`competitions-health.*` находятся в `deploy/systemd/`. Проверьте пути, пользователя,
владельца каталога `data/ops` и защищённый EnvironmentFile до установки.
Для rollback сохраните прежний app image и проверенный pinned NO-DELETE operations
bundle по [runbook](backup-reliability.md#rollback-без-удаления-резервных-копий).
Не возвращайте старые удаляющие backup-скрипты/units: app image откатывается отдельно
с read-only bridge backup.py/ops_state.py из bundle. На существующем VPS не
переустанавливайте шаблоны вслепую и не запускайте одновременно старую и новую
отправку.

Целевое расписание сохраняет существующие 03:15 МСК для local backup и
04:15 МСК для offsite; проверьте фактические следующие срабатывания через
`systemctl list-timers` и timezone хоста. Независимая проверка health работает
каждые 15 минут. `Persistent=true` позволяет догнать пропущенный запуск.

Offsite отправляет свежие `Verified` комплекты в существующий crypt remote,
без удаления объектов. Подтверждение отправки включает `rclone cryptcheck`.
`/admin/health` доступна только admin, показывает сохранённые результаты и
отличает неизвестные/просроченные проверки от успеха. Без бота Telegram остаётся
отключённым; это не считается подтверждением доставки.

Подробная процедура подключения, параметры и изолированный restore drill:
[backup-reliability.md](backup-reliability.md). Защищённые копии crypt-конфигурации
и паролей вне VPS обязательны для восстановления после потери сервера;
репозиторий не является местом хранения этих секретов.

### 6. Первый вход

Зайдите по `https://<ваш-домен>/` и войдите админом с паролем из `.env` —
он уже сильный: слабые значения не дали бы приложению стартовать. При
желании смените пароль в интерфейсе («Админ → Пользователи → Сменить
пароль»); смена отзывает активные сессии этого аккаунта.

## Сценарий Б. Перенос на другой сервер

Вся живая информация — это каталог `data/` (база, вложения, бэкапы) плюс
`.env`. Ничего больше переносить не нужно.

1. **Сделать бэкап на старом сервере (обязательно, до всего остального)**:

   ```bash
   python3 scripts/backup_sqlite.py \
       --db-path data/competitions.sqlite3 \
       --output-dir data/backups/sqlite \
       --files-dir data/files \
       --keep 14
   ```

   Убедитесь, что создан полный `Verified` комплект в `sets/<id>/`
   (БД, вложения, manifest), а не только один архив. Результат проверки
   архивов не заменяет изолированный запуск восстановленного приложения.

2. **Остановить старый инстанс** (чтобы база не менялась во время копирования):

   ```bash
   systemctl stop competitions-compose        # если есть юнит
   # или: docker compose down
   ```

3. **Скопировать на новый сервер** `data/` целиком и `.env` (scp/rsync —
   как удобно). На новом сервере должен быть клон репозитория той же версии
   (или новее — миграции схемы выполняются автоматически при старте).

   `data/` — живые данные: не терять, не «чистить по пути», не заменять
   на пустой каталог из свежего клона.

4. **Поднять на новом сервере**: шаги 3–5 сценария А (compose, nginx,
   бэкап-таймер). При первом старте приложение увидит существующую базу и
   подхватит её; учётки из `.env` не пересоздаются, если уже есть.

5. **Проверить** по списку ниже. Старый сервер держать выключенным, пока
   не убедились, что новый работает (иначе появятся расхождения данных).

## Типовые проверки после раскатки

- `curl http://127.0.0.1:8081/healthcheck` на сервере → `OK`; контейнер
  `docker ps` — статус healthy.
- Вход админом через браузер; смена пароля; выход/вход с новым паролем.
- Создать тестовую запись через «Добавить запись» — появилась в таблице.
- Отчёт: «Отчёты → Сформировать отчёт» с любым фильтром (условия живут в
  адресе страницы); «Экспорт» — скачивается xlsx.
- Вложение: прикрепить к записи PDF/PNG до 5 МБ — скачивается. Это заодно
  проверяет `client_max_body_size` в nginx.
- Бэкап: таймеры активны, свежий `Verified` комплект появился в
  `data/backups/sqlite/sets/`, offsite подтверждён и статусы не просрочены.

## Границы

- Один изолированный инстанс на организацию; мультиарендная платформа не
  предусматривается.
- Ответственность за персональные данные (оператор по 152-ФЗ, согласия,
  сроки хранения) несёт организация-владелец инстанса.
- Поддержка чужих внедрений не предполагается: код и документация — да,
  настройка и сопровождение чужих инстансов — нет. Подробнее — в
  [docs/future-ideas.md](future-ideas.md).
