# GTO-01/02: миграция и будущий релиз

Этот документ — план, а не разрешение production-операций. Работа выполняется
на синтетических изолированных БД. Merge, production deployment и restore
в этой задаче не разрешены.

## Модель и матрица legacy

Существующая строка student_gto_records уже содержала один факт результата.
Сохраняются таблица, ID, student_id, год, ступень, status, created_at/updated_at.
Снимается только UNIQUE(student_id,year,stage); nullable awarded_on добавляется
без выдуманной даты. Новая дочерняя award-сущность не нужна. Сертификатов ГТО
в старой модели не было; документы событий и вложения не переносятся.

| Legacy | После миграции | Наград |
|---|---|---|
| bronze / silver / gold | та же строка/ID/значения, дата NULL | 1 на строку |
| registered / participated | та же строка участия | 0 |
| неизвестный status / нарушенная student-связь | сохранён без исправления | доступ к сертификатам закрыт |
| пустая таблица | пустая таблица | 0 |

BEGIN IMMEDIATE сериализует startup нескольких соединений. Копирование с явными
ID, проверка равенства значений, замена таблицы, восстановление пользовательских
индексов/триггеров, high-water sqlite_sequence (даже удалённых ID), УИН,
метаданные сертификатов и финальный маркер gto_history_v1 — одна транзакция.
Прерывание любого этапа откатывает её; повторный startup проверяет форму схемы
и не дублирует факты. Неизвестные колонки/ограничения legacy блокируют rebuild,
а не молча отбрасываются. SQLite foreign_keys глобально не требуется:
новые записи, ownership, удаление и linkage защищены write-транзакциями.

## Перед будущим разрешённым релизом

1. Зафиксировать точные проверенные SHA и Docker image ID/digest, QA/CI PASS.
2. Создать Verified backup SQLite и всего дерева files штатным механизмом:
   quick_check, ZIP/manifest/hash и полнота ссылок. Не помещать backup в Git.
3. Снять приватную инвентаризацию старых GTO по ID/student_id/year/stage/status,
   timestamps, sqlite_sequence, строкам участия/награждений и всем файлам.
   Не публиковать персональные строки и УИН в отчётах/логах.
4. Восстановить backup в изолированной среде без production-подключений;
   выполнить миграцию точным образом, повторный обычный Sanic startup,
   quick_check и сравнение всех старых значений/файлов. Нарушенные legacy-связи
   отдельно разобрать, не выполнять автоматический merge или исправления.
5. После разрешённого релиза сверить количество строк и распределение статусов
   до/после: миграция не создаёт и не удаляет факты. Изменение структуры —
   снятие уникальности, nullable дата/УИН, новая пустая таблица сертификатов.
   Проверить старые ссылки/ID и чтение новых награждений/сертификатов.

## Rollback

Старый образ НЕ является автоматически совместимой целью: он не обслуживает
сертификаты и может удалить награду без очистки её metadata или перезаписать
исторический результат. Аддитивность некоторых колонок этого не доказывает.
После новых записей восстановление старой БД теряет награды/УИН/сертификаты.
Предпочтительны forward fix или отдельно проверенный совместимый code rollback
с сохранением всех данных и файлов. Автоматический restore старой БД запрещён.
Для явного restore требуется отдельное разрешение и safety backup текущих
данных по Production Operations.
