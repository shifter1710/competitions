# GTO-01/02: миграция и будущий релиз

Этот документ — план, а не разрешение production-операций. Работа выполняется
на синтетических изолированных БД. Интеграция main в A и A в B разрешена;
merge ГТО в main, production deployment и restore не разрешены.

## Модель и матрица legacy

Существующая строка student_gto_records уже содержала один факт результата.
Сохраняются таблица, ID, student_id, год, ступень, status, created_at/updated_at.
Снимается только UNIQUE(student_id,year,stage); nullable awarded_on добавляется
без выдуманной даты. Новая дочерняя award-сущность не нужна. Сертификатов ГТО
в старой модели не было; документы событий и вложения не переносятся.

| Legacy | После миграции | Наград |
|---|---|---|
| bronze / silver / gold | та же строка/ID/значения, дата NULL | 1 на строку |
| registered / participated | та же строка участия | 0 |
| неизвестный status / нарушенная student-связь | сохранён без исправления | доступ к сертификатам закрыт |
| пустая таблица | пустая таблица | 0 |

BEGIN IMMEDIATE сериализует startup нескольких соединений. Копирование с явными
ID, проверка равенства значений, замена таблицы, восстановление пользовательских
индексов/триггеров, high-water sqlite_sequence (даже удалённых ID), УИН,
метаданные сертификатов и финальный маркер gto_history_v1 — одна транзакция.
Прерывание любого этапа откатывает её; повторный startup проверяет форму схемы
и не дублирует факты. Неизвестные колонки/ограничения legacy блокируют rebuild,
а не молча отбрасываются. SQLite foreign_keys глобально не требуется:
новые записи, ownership, удаление и linkage защищены write-транзакциями.

## Перед будущим разрешённым релизом

1. Зафиксировать точные проверенные SHA и Docker image ID/digest, QA/CI PASS.
2. Создать Verified backup SQLite и всего дерева files штатным механизмом:
   quick_check, ZIP/manifest/hash и полнота ссылок. Не помещать backup в Git.
3. Снять приватную инвентаризацию старых GTO по ID/student_id/year/stage/status,
   timestamps, sqlite_sequence, строкам участия/награждений и всем файлам.
   Не публиковать персональные строки и УИН в отчётах/логах.
4. Восстановить backup в изолированной среде без production-подключений;
   выполнить миграцию точным образом, повторный обычный Sanic startup,
   quick_check и сравнение всех старых значений/файлов. Нарушенные legacy-связи
   отдельно разобрать, не выполнять автоматический merge или исправления.
5. После разрешённого релиза сверить количество строк и распределение статусов
   до/после: миграция не создаёт и не удаляет факты. Изменение структуры —
   снятие уникальности, nullable дата/УИН, новая пустая таблица сертификатов.
   Проверить старые ссылки/ID и чтение новых награждений/сертификатов.

## Полнота резервных копий сертификатов

`src/backup.py:reference_names` перечисляет каждую строку
`student_gto_certificates` как `gto/<gto_record_id>/<stored_name>` и отклоняет
неположительный ID или небезопасное имя. Если таблицы ещё нет, старый формат
БД сохраняет прежнее поведение. Полный backup проверяет наличие каждого файла
в исходном дереве, запрещает symlink и сверяет список ссылок с ZIP при
`verify_set`; изолированное извлечение повторно проверяет файлы. Отсутствующий
сертификат при сохранённой metadata блокирует статус Verified.

Это проверка полноты ссылок, а не доказательство успешного запуска приложения
после restore. Перед production-миграцией всё ещё нужны отдельные Verified
backup, изолированное восстановление и сравнение приватной инвентаризации:
цепочка студент → награждение → сертификат, metadata, размеры и хеши файлов до
и после restore. Эти production-проверки здесь не выполняются и их PASS не
заявляется.

## Rollback

Старый образ НЕ является автоматически совместимой целью: он не обслуживает
сертификаты и может удалить награду без очистки её metadata или перезаписать
исторический результат. Аддитивность некоторых колонок этого не доказывает.
После новых записей восстановление старой БД теряет награды/УИН/сертификаты.
Предпочтительны forward fix или отдельно проверенный совместимый code rollback
с сохранением всех данных и файлов. Автоматический restore старой БД запрещён.
Для явного restore требуется отдельное разрешение и safety backup текущих
данных по Production Operations.

## Совместимый кандидат code rollback для GTO-03

PR B добавляет только отчёт/навигацию и не меняет схему относительно PR A.
Точный кандидат для отката кода B → A:

- интегрированный PR A с проверкой GTO references: `c2f8fdddab0c1087a4317b6f97049419640e1fdb` ([PR 20](https://github.com/shifter1710/competitions/pull/20));
- точный image ID нового A фиксируется в CI совместной версии, а не берётся
  из старой сборки до интеграции main.

A уже поддерживает стабильные награждения/УИН/сертификаты, в отличие от
старого main до этой миграции. Перед признанием конкретного B → A rollback
проверенным нужно открыть синтетическую БД после B обычным A startup,
сравнить записи/файлы/флаги, прочитать новые награды/сертификаты и выполнить
quick_check БЕЗ restore или замены БД. Результат этой проверки фиксируется
в QA/runtime отчёте; известный SHA/image сам по себе не подменяет такую проверку.
Нужно также иметь доступный воспроизводимый артефакт точного образа для будущего
релиза: указанный CI image ID — идентификатор проверенной сборки, не обещание
наличия опубликованного registry-образа. Автоматический restore по-прежнему запрещён.

## Повторение проверок

Используйте QA-OPT-02 из docs/qa-opt-02.md и отдельное синтетическое окружение.
Targeted: src/gto_test.py, src/gto_history_test.py, src/gto_certificates_test.py,
src/gto_report_test.py, src/gto_navigation_test.py и GTO/profile/delete сценарии src/main_test.py. Затем полный regression,
pre-commit all-files, independent QA, обычный Sanic fresh/legacy/repeat startup.
GTO exact-image workflow проверяет точный head PR; локальный доступ к Docker
может быть недоступен — это ограничение среды, а не доказательство image PASS.
Для PR B отдельный job собирает точные SHA A и B и запускает B → A → B на
одном синтетическом Docker volume без восстановления БД. Он сверяет ID,
УИН, metadata и хеши сертификатов после каждого переключения; SHA и image ID
обоих образов публикуются в summary этого CI-запуска.

Отдельный JS safe-return regression (`gto_navigation_test.py`) выполняется
существующим Node в обычном QA/полном CI. В production Python-образ Node не
добавляется; `gto_report_test.py` содержит полный HTTP/XLSX report matrix и
целиком выполняется внутри exact-image CI без Node и без исключения тестов.
