# Student Profile P2 — реальная карточка студента

База: Event Page P1 `b80081d`; отдельная ветка `feature/student-profile-p2`.
Визуальная основа — Concept A v2 `123b3c6`. Стек сохранён: Jinja2,
Bootstrap, vanilla JavaScript и существующая SQLite. Новых зависимостей нет.

## Исходное состояние и композиция

Раньше актуальные данные, образование, ГТО, псевдонимы и связанные данные
шли последовательно; история находилась после нескольких больших блоков.
Теперь один заголовок ФИО, статус, институт/группа, текущий расчётный курс и состояние
доступа предшествуют пяти вкладкам. История открыта первой. Правка карточки,
добавление ГТО, других имён и редкие операции раскрываются по запросу.

Пятый раздел «Данные и образование» нужен сверх четырёх вкладок прототипа:
он сохраняет полную форму актуальных данных, сведения из справочника группы,
активацию и удаление карточки. Курс вычисляется по текущей группе и дате приложения Asia/Omsk, ручного поля нет. Год поступления, длительность, учебный год и предупреждение о
предполагаемом завершении обучения остаются в образовательном разделе.

ссылки объединённых карточек. Frontend не создаёт обходов этих проверок.
Атлет не получает доступ к штатной карточке; его кабинет не изменён.

## Разрешённое расширение read-only контекста

По отдельному согласованию владельца SELECT истории дополнен существующими
полями `discipline`, `position`, `result`, `calendar_event_id`, `extra_data`.
Предикат `student_ref_id = ?` и порядок `date DESC, id DESC` сохранены.
С 2026-10-19 период (учебный год или произвольный диапазон с включительным
пересечением дат) применяется в SQL до `LIMIT 50`. Предыдущая/следующая
страницы используют `offset` и сохраняют период, вкладку и безопасный возврат.
Глобальное количество связанных участий показывается отдельно от выбранного
периода и количества загруженных/найденных строк. Поиск остаётся клиентским
среди показанных записей. История однофамильца и несвязанные записи не подмешиваются.

При пустых базовых discipline/result применяется существующий
`event_participation_effective_values` с активными custom fields. Это только
представление: исторические строки, extra_data и связи не обновляются.
Место и свободный текст результата отображаются независимо: нулевое место —
«Без места», пустой текст — «Не указан». «Неявка» остаётся текстом результата.
Схема, миграции, модели идентификации и авторизации не изменены.

## Состояния и взаимодействия

Без JavaScript все разделы и native POST формы доступны последовательно.
С JavaScript вкладки имеют tab/tabpanel роли, управление стрелками/Home/End.
Формы отправляются на те же URL тем же FormData с прежним CSRF. Adapter
распознаёт `admin_error` в финальном redirect, а не считает любой HTTP 200
успехом. При ошибке введённые поля остаются в DOM, сообщение получает фокус,
можно повторить отправку или отменить ввод. Повторная отправка блокируется
до ответа; отключение кнопок/полей и `aria-busy` обозначают выполнение.
Истёкшая сессия не считается успешным сохранением.

Несохранённая форма блокирует переход на другую вкладку и предупреждает
при уходе со страницы. Отмена восстанавливает исходные поля. Другие формы
не отправляются поверх незавершённого ввода. На успехе сервер перечитывается;
в URL возвращаются tab/history_q, период, offset и безопасный return. Одноразовый sessionStorage
контекст хранит только время, прокрутку и ID вкладки для фокуса, живёт 60 секунд
и удаляется после чтения. Ни формы, ни пароли, ни сведения аккаунтов в storage
не сохраняются. Введённый поиск присутствует только в URL/живом поле.

Возврат принимает только тот же origin и путь `/admin/people` либо
`/calendar/<число>`. Если исходный URL отсутствует, гарантирован только возврат
в список студентов. Новые поля навигации не меняют backend-контракт.

## Адаптивность и отличия от прототипа

Используются существующие семантические CSS-токены обеих тем. Все новые правила
ограничены `.person-page`; P1 Event не перерабатывается. На ширине до 900 px
история становится вертикальными записями с видимыми подписями. На телефоне
также доступны все поля и действия ГТО/других имён/аккаунтов без прокрутки
всей страницы. DOM и IDs не дублируются.

В отличие от прототипа сохранены реальные исторические снимки, связь аккаунтов,
полная образовательная сводка и реальные ограничения. Нет фиктивного сезона,
командных очков, статусов результата или демо-операций. Длинная история —
постраничная выборка по 50 связанных участий с необязательным периодом;
старые участия доступны при выборе соответствующего учебного года.

## Верификация и ограничения

Новые проверки покрывают read-only projection, 50-row cap, tie-break по ID,
изоляцию однофамильцев/несвязанных записей, legacy fallback/base priority,
отсутствие записей в БД при GET, пять вкладок и ролевые формы. Существующие
person/reconciliation/identity/GTO/access/education и P1 проверки сохраняются.
Результаты реальных запусков и независимой browser QA приводятся в отчёте
задачи; наличие этого документа само по себе не означает QA PASS.

**Отдельный незакрытый release gate P1:** исходный полный запуск P1 содержал
три устаревших UI assertion; после их исправления прошли целевые тесты.
Перед merge/release P1 нужен полный повторный прогон именно P1. Полный прогон
P2 не считается автоматическим закрытием этого отдельного требования.

## GTO-01/02: УИН и история награждений

Во вкладке ГТО показан персональный текстовый УИН (admin редактирует,
editor/viewer читают) и отдельные награждения одного года/ступени. «Добавить
запись ГТО» сохраняет новый факт; «Исправить запись» меняет выбранный ID.
Дата необязательна. PDF/PNG/JPEG сертификаты прикрепляются к конкретной
награде, по одному файлу за операцию, без замены других документов. Admin/editor
управляют наградами и документами; viewer читает, athlete видит собственные
файлы в существующем кабинете. Native forms/details/подтверждения и мобильные
подписи работают без JavaScript. [Полный workflow](gto-workflow.md).
