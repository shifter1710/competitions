# TEAM-01/02: команды события, история и документы

## PR A — команды и состав

Во вкладке «Команды и результаты» страницы соревнования создайте команду,
откройте её и отметьте конкретные участия. ФИО с разными дисциплинами —
разные строки. Одно участие может входить в несколько команд; повтор пары
команда/участие не создаёт дубль и вторую запись истории. Пустой состав допустим.
Поиск скрывает строки, сохраняя отмеченные участия. Список всегда использует
все участия события, независимо от фильтра мест основной страницы.
Основные формы работают без JavaScript; поиск без JavaScript не скрывает строки.

Добавление/исключение меняет только выбранные участия и не заменяет весь состав,
поэтому параллельная работа операторов не теряет чужие изменения. Ошибка одного
ID откатывает весь набор. Несвязанные с карточкой участия разрешены в составе,
но не предоставляют доступ через кабинет. Связь по ФИО, owner_id или хешу
не создаётся. Управление — admin/editor, просмотр — viewer; athlete не получает
доступ к странице события или новым операциям изменения.

Смена эффективной дисциплины исключает участие из всех команд с причиной
`discipline_changed`; повторное включение выполняется явно. Используется прежняя
нормализация пробелов/регистра и fallback активного custom-поля «Дисциплина».
Правка определения этого custom-поля также учитывается. Изменение места или
результата не влияет на состав. Удаление участия очищает членства атомарно,
история остаётся. Перепривязка карточки сохраняет состав, но записывает старую
связь и новый ID в историю; следующий запрос использует новую связь.

Команду можно удалить только без действующих членств, связанных результатов
и документов. Документы проверяются независимо от режима доступа. Удаление
события с командами запрещено: сначала необходимо явно обработать их связи.
История всех команд доступна по `/calendar/<event_id>/teams`, включая удалённые
команды. В истории — снимок названия команды, ID участия, имя и эффективная
дисциплина участия, ID карточки на момент действия, время UTC, инициатор и
причина. Никаких восстановленных/предполагаемых прошлых составов нет.

Командный результат получил необязательный выбор команды этого события.
Старые строки имеют `team_id = NULL`. Категория уникальна внутри выбранной
команды, а прежние строки без команды сохраняют прежнюю уникальность категории.
Личные места, отчёты и подтверждение результатов этим не изменяются.

## SQLite и жизненный цикл

| Объект | Изменение | Существующие данные |
| --- | --- | --- |
| `calendar_event_teams` | Команда с одним неизменяемым event ID | Нет автоматического наполнения |
| `calendar_event_team_members` | PK `(team_id, competition_id)` | Только явные действия |
| `calendar_event_team_history` | История с минимальными снимками, без каскада удаления | Начинается с новых действий |
| `calendar_event_team_results.team_id` | Nullable ID команды | NULL |
| `calendar_event_documents.team_id` | Nullable ID команды, используется в B | NULL; прежние назначения/файлы сохранены |

TEAM-миграция аддитивная, выполняется в одном SAVEPOINT и идемпотентна.
Нет глобального включения foreign_keys, триггеров с Python-функциями или
переписывания storage других доменов. Проверка принадлежности + изменение
состава выполняются под `BEGIN IMMEDIATE`; разные SQLite-соединения используют
блокировку SQLite, а не только Python RLock.

CRUD/inline/подтверждение импорта используют `update_competition`; удаление
одиночной записи, записи с вложениями, очистки по дате/всего реестра используют
обёртку одной транзакции. В той же транзакции проверяются прежние действующие
членства, сохраняется история и очищаются изменённые связи. Ручная/пакетная
привязка участия к карточке или событию проходит тот же контроль. Импорт новых
записей не создаёт составы; restricted batch обновляет только место/результат.
Обычные операции не «ремонтируют» чужие orphan-связи. Прямая ручная SQL-правка
в обход storage не является поддерживаемым пользовательским workflow.

## Защитная совместимость PR A

A резервирует `team_id`, но ещё не выдаёт командные документы атлетам.
Документ с ненулевым team_id или неизвестным access_mode не попадает в кабинет
и запрещён для прямого скачивания athlete, даже при оставшемся старом
selected_students назначении. Служебное скачивание admin/editor/viewer сохранено.
Обычные generic/protocol операции не меняют и не удаляют такую запись/файл;
удаление её события также блокируется. UI показывает неподдерживаемый режим
отдельно, не превращая его в «все участники» или «выбранные студенты».

## PR B и план выпуска (до отдельного разрешения владельца)

B добавляет режим `team_members` в существующий механизм event documents:
одна запись, один физический файл, одна команда того же события. Выберите
«Текущий состав команды» и команду в форме документа, либо откройте загрузку
из карточки команды. Форма работает без JavaScript. При ошибке сохраняются
название, режим, команда и выбранные карточки; файл нужно выбрать повторно.
В кабинете документ показан один раз с названием команды, даже если у карточки
несколько участий в составе. Персональные назначения для этого режима не создаются.

Один SQL-предикат для списка и скачивания проверяет актуальную цепочку
аккаунт → student_ref_id → существующая карточка → существующее участие в этом
событии → действующее членство → команда документа в том же событии.
История, ФИО, owner_id, хеши, активность карточки, модерация участия и REP-05
не предоставляют и не ограничивают этот доступ. Аккаунт должен быть активен.
Изменение состава или перепривязка немедленно меняет доступ к уже загруженному
файлу без копирования/переименования файла. Осталась одна из нескольких
строк участия в составе — доступ сохраняется; исключена последняя — отзывается.

Скачивание повторно читает cookie/password version, текущую роль/карточку
аккаунта, документ и его ACL после асинхронного чтения файла. При изменении
документа или версии файла ответ не содержит прочитанные байты. Чтение не
следует символическим ссылкам, ограничено прежним лимитом размера; служебные
имена проходят прежнюю строгую проверку. Кабинет и скачивание, включая отказы,
имеют `Cache-Control: private, no-store`.

Правка только названия или замена файла без полей доступа сохраняет режим,
команду и назначения. Явная смена режима разрешена admin/editor. Протоколы
по-прежнему доступны всем участникам события; старые `all_participants` и
`selected_students` сохраняют свои правила. Запись документа и назначений
атомарна, при отказе записи новый файл удаляется, прежний остаётся.

Проверки B описаны в `src/team_documents_test.py`: настоящий upload одного
файла двадцати получателям, live ACL, оборванные цепочки, повторная проверка
после read с изменениями отдельным SQLite-соединением, замена файла, ошибки
хранилища и сохранение настроек формы. Результаты независимой QA, полного
regression, браузера, exact-image CI и A-on-B добавляются в review после
исполнения; наличие теста само по себе не является PASS.

1. Проверить оба точных SHA, независимую QA, regression, браузер и Docker CI.
   PR B зависит от A; порядок слияния A → B. Слияние/production пока запрещены.
2. Перепроверить актуальный main и REP-05. Базовый main `216452b` ещё содержит
   прежний startup backfill связей календаря; TEAM его не копирует и не изменяет.
   При проверке 2026-10-21 REP-05 ещё отдельная ветка (наблюдавшийся head
   `1994c5e52a0db5d464dcf0b3483e45b5ca8d1fb7`); перед интеграционным
   доказательством заново проверить оба head, не считать этот SHA последним навсегда.
   Перед выпуском обязательна совместная проверка с merged REP-05 и отсутствием
   отменённой startup-автопривязки. При отсутствии этого доказательства — блокер.
3. После разрешения владельца перед миграцией создать Verified backup SQLite
   и вложений по действующей процедуре. Проверить manifest, SQLite quick_check,
   ZIP CRC и сохранность предыдущего состояния. Соблюдать действующий NO-DELETE
   ops bundle; не менять S3, Telegram или backup jobs ради TEAM.
4. Сначала выпустить A, проверить startup/health и сохранность старых данных.
   Затем B: проверить старые документы/протоколы, добавление и отзыв доступа.
5. Цель отката B — точный проверенный образ A, а не более старый main.
   Обязателен A-on-B тест на синтетической БД, полученной реальными операциями B:
   A не выдаёт/не преобразует/не удаляет командные документы и историю.
   Проверенный ниже raw A target не заменяет совместную проверку с REP-05:
   итоговая цель отката должна также сохранять отсутствие startup-автопривязки.
6. При откате кода оставить аддитивные таблицы/колонки и файлы. Восстановление
   старой БД не является штатным откатом кода и не подразумевается разрешением
   на deployment. Уже полученные байты невозможно отозвать; проверяется отказ
   запросам, начавшимся после commit отзыва, и повторная проверка после чтения файла.

Локальный Docker может быть недоступен из-за прав на socket. В таком случае
точный образ проверяет выделенный CI job: checkout head SHA, revision label,
image ID, запуск дважды с синтетическим volume, HTTP smoke и TEAM-тесты внутри
образа. Успех локального Python не считается успехом Docker до зелёного CI.

## Статус доказательств перед review B

На 2026-10-21 локальный selfcheck рабочих изменений B поверх A: TEAM-набор
49 PASS, прежние документы/протоколы и API хранилища 52 PASS. Независимый
целевой набор B: 88 PASS, без ошибок и пропусков; один тест защитного режима,
применимый только к A, намеренно исключён из B-набора. Это целевые проверки,
а не утверждение об итоговом полном regression, браузере или CI.

Сценарий одного настоящего HTTP upload проверяет скачивание одних байтов
двадцатью аккаунтами, одну строку документа, один файл и отсутствие персональных
назначений; добавление/исключение состава не создаёт копий.

Независимый raw A-on-B выполнен с точным кодом A
`e2f7c867660ad0ec00ab2bfd821800201094d121` на синтетической БД и файлах,
созданных реальными HTTP-операциями B. После двух запусков A проверены:
семь таблиц и четыре файла неизменны; командный документ недоступен athlete;
оставшееся старое персональное назначение не предоставляет доступ;
три прежних документа доступны по прежним правилам; служебное скачивание
сохраняет байты; попытки изменения/удаления командного документа не меняют
БД и файлы. Это проверка конкретного raw target и fixture, не доказательство
безопасности startup для произвольных старых данных с совпадающими названиями
и датами при `calendar_event_id = NULL`.

Наблюдавшийся main остаётся `216452be961b0a33e5290e4b053d1e4f6018e6b0`,
REP-05 `1994c5e52a0db5d464dcf0b3483e45b5ca8d1fb7` ещё не слит. Raw A
наследует прежнюю startup-автопривязку; проверка отсутствия автопривязки
и совместного отката A+REP-05 на B+REP-05 остаётся отдельным обязательным
условием выпуска. Изолированное интеграционное дерево само по себе не PASS.
Полный regression, браузер, точные образы и интеграционные результаты
фиксируются после исполнения в review PR с SHA и логами; одни числа тестов
не закрывают эти условия. Разрешения на production в рамках разработки нет.
