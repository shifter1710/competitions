# QA-OPT-02: безопасная оптимизация pytest

Изменения касаются только тестов и документации. Производственная логика,
схема SQLite, зависимости и полный состав существующей регрессии сохранены.

## Среда и исходная точка

- Функциональная база: `25ca27a139f8779a55665a81758873e3147eb2f5`.
- Python 3.10.21; Sanic 25.12.1, sanic-testing 24.6.0,
  sanic-ext 25.12.0, pytest 7.3.1. Полный freeze исходного и отдельного
  тестового окружений совпадает; зависимости не обновлялись.
- Локальный Intel Core i7-11700F, 16 логических CPU, 31.2 GiB RAM.
  Временные SQLite-файлы: ext4 на HDD TOSHIBA HDWD120 (`/dev/sda2`).
  Прогоны последовательные, без другого тяжёлого pytest или Docker build.
- Чистое отдельное worktree, синтетические AUTH-настройки, отдельные
  временные data/tmp, свободные зарезервированные loopback-порты.
- PR #16/REP-05 не объединялся, его миграция не выполнялась.

## Подтверждённые причины

Полный исходный прогон: **1539 passed**, 0 failed/skipped/xfail,
4463 warnings; pytest **3705.91 s**, внешнее wall-clock **3707.343 s**,
максимальный RSS **1120320 KiB**. Это один полный исходный замер,
а не устойчивая медиана.

Округлённые нижние границы суммарных фаз: setup 1508.53 s, call 2117.41 s,
teardown 54.06 s. 1850 фаз короче 5 ms скрыты стандартным выводом durations;
эти суммы не являются точными профилями всех фаз. main_test.py занимает
2663.20 s, storage_test.py — 471.10 s. Локальный вклад диска существенен:
при storage-тестах наблюдалось ожидание журнала ext4
`jbd2_log_wait_commit`. Выводы старого CI о небольшой доле storage нельзя
переносить на этот HDD.

Отдельное профилирование 12 исходных сценариев показало 57 циклов
старта/остановки Sanic, 28.72 s внутри app.run, 7 созданий SQLiteAdapter
с суммарными 13.50 s и 60 вызовов подготовки password hash за 1.67 s.
Метрики включающие и перекрываются: складывать их нельзя. Профилировщик
увеличил время пилота до 49.70 s; это не wall-clock benchmark.

В отдельном профилируемом сценарии из 162 одинаковых HTTP healthcheck
число signal routes выросло с 220 до 540, а capture middleware на маршруте —
с 3 до 163. Медиана первых десяти наблюдаемых повторных запросов была
0.3468 s, последних десяти — 0.4456 s. Повторный startup и накопление
состояния подтверждены наблюдением, а не размером тестового файла.

## Принятые изменения

HTTP-сценарий получает новую сборку настоящего приложения через runpy,
новый mock/storage и собственный лениво запускаемый сервер. Первый запрос
выполняется после установки SQLite-фикстуры. Сервер переиспользуется только
между запросами этого теста, затем закрывается вместе с сокетом и loop.

Сохраняется транспорт установленного SanicTestClient: новый HTTPX-клиент
на каждый вызов, исходные redirects/allow_redirects, cookies только внутри
одной цепочки редиректов, первый собранный Sanic Request. Middleware,
авторизация, CSRF, настоящие handlers и startup/shutdown выполняются.
Capture middleware регистрируется один раз до startup.

Разделены login/import/presence dictionaries и app aliases. Два глобальных
OpenAPI singleton sanic-ext изолируются через их reset() с точным
восстановлением прежних ссылок. После teardown очищаются только два
известных functools lookup cache Router, удерживающих app через ключ self;
маршруты, сигналы и middleware не удаляются. Сохраняется прежний текущий
loop без создания постороннего loop для его снимка. Это test-only
совместимость с зафиксированными установленными версиями.

Прежнее глобальное увеличение recursion limit до 10000 удалено. Регрессия
12 раз собирает и запускает настоящее приложение с лимитом 1000,
проверяет постоянный размер signal routes и сборку закрытых app графов GC.

Подготовка synthetic user hash кешируется только в fake_get_user:
ограниченный кеш 32, ключ содержит пароль, все четыре SCRYPT-параметра,
идентичности hash_password и scrypt. Для каждого вызова возвращается новый
словарь пользователя. Production hash/verify/login/password-change не
подменяются; реальные проверки правильного и неправильного пароля,
смены пароля и случайных salts остаются.

Короткий пилот A стал медленнее: новая полная сборка приложения для каждого
теста платит стоимость холодного старта sanic-ext HEAD/OPTIONS. Профиль
показывает, что добавление автоматических handlers после finalize вызывает
повторную финализацию signal router. Эти handlers и конфигурация не
отключались ради скорости. В промежуточном варианте устранение роста истории запросов ускорило
длинный однотипный сценарий на 90.7%, но это отдельный профилируемый
эксперимент, не результат полного suite.

Отклонены: общий сервер между тестами (порт остаётся открыт после теста),
клонирование подготовленного app (нет подходящего публичного API),
обёртка startup в app.amend (reset мешает dispatch сигнала), отключение
HEAD/OPTIONS/docs, изменение production-кода и обновление зависимостей.
xdist и массовое объединение тестов не внедрялись. tmpfs оценивается
отдельно от сравнения A/B на одинаковом HDD.

Для B сокращение повторной подготовки подтверждено счётчиком 300 → 1,
а real verify правильного и неправильного пароля выполнен после каждого
микрозамера. Медиана короткого A+B пилота на 3.1% ниже A, но на 43.7% выше
исходного пилота; это промежуточный холодный вариант, а разброс не позволяет
приписывать все различия кешу.

Финальное дополнение HTTP-фикстуры использует исходный зарегистрированный
callback sanic-ext для подготовки HEAD/OPTIONS **до** app._startup. Публичный
app.ext инициализирует расширения; затем читается одна private регистрация
_future_listeners с проверкой точных версий трёх пакетов, event,
module/qualname, единственности callback и default HTTP/OpenAPI flags.
Callback не заменяется и не удаляется: настоящий normal startup вызывает
его снова. Его guards не добавляют уже существующие HEAD/OPTIONS.
Неподдерживаемые версии/настройки/регистрация вызывают явный отказ до HTTP.

Паритет canonical prepare_methods=False и prepared проверяется настоящим
HTTP при default и явно разрешённом синтетическом CORS origin: полная
конфигурация, маршруты/requirements/strict_slashes/unquote, provenance и код
handlers, порядок middleware, реальные signal callbacks/conditions/priority,
listener inventory и OpenAPI JSON равны. Явные пользовательские HEAD/OPTIONS,
Allow, auth и CSRF сохранены. Наблюдение исходного callback подтверждает
один framework вызов в canonical и два вызова в prepared (ранний + framework),
с сохранением объекта исходной регистрации.

Различие числа signals классифицировано: каждый исключённый резервный
sanic.__signal__.__init__ проверяется как точный upstream sanic.signals._blank
с тем же code object, priority 0 и без conditions. Меньше finalize — меньше
повторных noop регистраций; реальные сигналы совпадают без дедупликации.
Отдельно fixture восстанавливает только известный framework-owned env key
SANIC_LOG_EXTRA (отсутствие/значение) после успеха и исключения. Это не
утверждение о полном сбросе глобального logging formatter.

Финальный короткий пилот: медиана 23.659 s против 31.175 s исходного,
сокращение 24.1% по трём повторам, диапазон 22.896–25.166 s. Отдельный профиль
показывает 11 настоящих startup/shutdown, 22 вызова исходного _add_handlers
за 3.55 s вместо 11 за 43.86 s в холодном варианте. SignalRouter.finalize
выполнен 11 раз за 0.035 s. Число real verify_password scrypt осталось 11,
как в исходном пилоте; подготовительные hash вызовы сократились с 60 до 16.
Профилируемое время 29.20 s не смешивается с обычным wall-clock benchmark.

## Повторение локально

Используйте отдельный checkout без `.env`, зависимости из requirements.txt
и доступный в PATH Node (в замерах — 22.14.0). Не запускайте замеры параллельно
с тяжёлыми тестами или сборками. Пример полностью синтетического окружения:

```bash
qa_run="$(mktemp -d /tmp/competitions-qa.XXXXXXXX)"
mkdir "$qa_run/data" "$qa_run/tmp"
qa_env() {
  env -i PATH="$PWD/venv/bin:$PATH" HOME="$qa_run" \
    LANG=C.UTF-8 LC_ALL=C.UTF-8 PYTHONHASHSEED=0 \
    AUTH_SECRET_KEY=ci-synthetic-secret-key \
    AUTH_ADMIN_PASSWORD=ci-synthetic-admin-pass-123456 \
    AUTH_EDITOR_PASSWORD=ci-synthetic-editor-pass-123456 \
    AUTH_VIEWER_USERNAME=viewer \
    AUTH_VIEWER_PASSWORD=ci-synthetic-viewer-pass-123456 \
    DATA_FOLDER="$qa_run/data" DATABASE_PATH="$qa_run/data/synthetic.sqlite3" \
    TMPDIR="$qa_run/tmp" \
    "$@"
}
qa_pytest() {
  qa_env "$PWD/venv/bin/python" -m pytest "$@"
}

# Быстрые контракты тестовой инфраструктуры.
qa_pytest src/http_scenarios_test.py src/password_preparation_test.py -q

# Полный regression, включая collection, все исходные и новые случаи.
qa_pytest src/ -q --durations=0 --junitxml="$qa_run/junit.xml"

# Быстрый полный локальный прогон: скрипт сам проверяет свободное место,
# создаёт уникальный basetemp в tmpfs и удаляет только свой каталог.
qa_env ./scripts/pytest_tmpfs.sh src/ -q --junitxml="$qa_run/tmpfs-junit.xml"
./venv/bin/pre-commit run --all-files
```

Каталог qa_run сохраняется для анализа; удаляйте только свой созданный
каталог, когда результаты больше не нужны. Для сопоставимых замеров создавайте
новый qa_run на каждый запуск. tmpfs требует доступного /dev/shm и запаса
места по проверке скрипта; такая смена файловой системы отражается отдельной
строкой результатов и не подменяет сравнение A/B на HDD. Не передавайте
вручную существующий ценный каталог в --basetemp: pytest удаляет его содержимое.

Production, рабочая БД, S3, Telegram и чужие worktree не изменялись.
Миграций, UI-изменений и новых runtime-зависимостей нет.
