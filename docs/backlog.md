## Задачи

### 1. ~~UI для merge-инструмента~~ — ✅ сделано (2f87629, в dev)
API готов (`POST /admin/students/merge`: без `confirm` возвращает превью
`records_to_merge`, с `confirm` выполняет; `rewrite_names` — перезапись
отображаемых ФИО). Нужна страница/секция в админке: два поля ФИО,
кнопка «Предпросмотр» → показать счётчик → чекбокс «переписать ФИО в
записях» → «Объединить» с подтверждением. Form-encoded, CSRF как обычно.

### 2. ~~Подсказка существующих ФИО при заполнении профиля~~ — ✅ сделано (8b86910 + 7420d3e, в dev; приватность — см. data-model-decisions.md)
Привязка записей посимвольная: «Иванов И. И.» ≠ «Иванов Иван Иванович»,
опечатки ломают привязку чаще, чем тёзки. Бэкенд: `GET /api/students` —
уникальные ФИО из записей. Фронтенд: datalist в форме профиля и в
админской привязке псевдонима. Статус: согласовать с владельцем.

### 3. ~~Аудит-журнал безопасности~~ — ✅ сделано (бэкенд + минимальная страница /admin/audit, в dev; решение — data-model-decisions.md)
Таблица + записи: входы (успешные/нет), смена паролей, действия модерации
(подтвердить/отклонить с комментарием), merge. Просмотр — страница админа.
Обсуждалось как недостающие 20% «спокойной» аутентификации.

### 4. Пагинация таблицы — Б + Ф, «на триггере»
Триггер: записей заметно больше ~500–1000 или массовый приход атлетов.
Серверная постраничная выдача, фильтры/сортировка на сервере, экспорт
по-прежнему выгружает всё.

### 5. 2FA (TOTP) для админов — Б + Ф, опционально
Обсуждалось как желательное для «городского» сценария; для доверенного
круга не нужно.
