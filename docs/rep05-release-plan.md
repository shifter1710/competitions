# REP-05: план миграции и production release

Production-обновление требует отдельного решения владельца. Этот документ
описывает подготовленный порядок; сам по себе не разрешает миграцию.

## Матрица SQLite

| Объект | Изменение | Имеющиеся данные | Новые данные |
|---|---|---|---|
| calendar_events.results_confirmed | INTEGER NOT NULL DEFAULT 0 | Однократно 1 | 0 |
| calendar_events.results_confirmed_at | TEXT NULL | NULL | UTC при подтверждении |
| calendar_events.results_confirmed_by | INTEGER NULL | NULL | ID admin при подтверждении |
| competitions.position | Без DDL/перезаписи | Нули, строки и история сохранены | Число / DNF, пустое → 0 |
| competitions.calendar_event_id | Без DDL; startup-автосвязывание отключено | NULL и существующие ссылки сохранены | Только явные event-workflows / связывание |
| review_status, result, extra_data, identity, вложения | Без миграции | Сохранены | Прежний контракт |

Три ADD COLUMN и UPDATE legacy-событий выполняются в SAVEPOINT. Наличие
results_confirmed — маркер завершения; ошибка откатывает весь блок. Новый пустой
файл БД создаётся сразу с DEFAULT 0. Повторная инициализация не меняет ручное
состояние. Startup-автосвязывание P0 отключено: совпадение названия и дат, даже
единственное, не меняет NULL-записи. Прежние ссылки не снимаются и не переназначаются;
явное ручное/admin batch связывание сохранено. Проверить raw ссылки и Reports
несвязанной истории до/после повторного startup, включая совпадающее неподтверждённое
событие (синтетический oracle: 1 участие / 1 победа остаются 1 / 1).

## Preflight перед отдельным одобрением deployment

1. Зафиксировать точные целевой SHA с QA/CI PASS и текущий production SHA.
   Проверить актуальный main и совместимость с параллельной инфраструктурной
   задачей; релизы выполнять последовательно.
2. Прочитать схему и статус приложения без раскрытия данных. Подсчитать события,
   наличие миграционных колонок и linked/unlinked participation counts; не
   менять production-записи ради проверки. Зафиксировать исходные агрегаты.
3. По штатной процедуре остановить записи перед финальным снимком и startup.
   Создать свежие SQLite-safe backup базы и архив вложений установленным
   `scripts/backup_sqlite.py` / `src/backup.py`; сохранить вне Git. Проверить
   существование/читаемость обоих артефактов, восстановленную временную SQLite
   через `PRAGMA quick_check`, ZIP CRC вложений через `ZipFile.testzip()` (ожидается
   `None`) и состав архива без публикации содержимого. Зафиксировать SHA ревизии,
   размеры и SHA-256 обоих backup-артефактов в release-записи вне Git.
4. Сохранить предыдущую рабочую ревизию, конфигурацию и путь backup; подготовить
   существующий штатный способ возврата версии. Не менять nginx/systemd/секреты.

## Если BACKUP-02 / PR14 уже установлен

Использовать действующий [runbook BACKUP-02](backup-reliability.md), сохраняя его
операционные гарантии. Перед миграцией нужен **полный Verified** комплект
`source=release`: `database.sqlite3.gz`, `files.zip` и `manifest.json`. Не считать
`Completed` или `database_only` успешной предрелизной точкой. Зафиксировать ID
комплекта, SHA/размеры архивов и независимый SHA-256 manifest вне Git; проверить
штатным verifier gzip, quick_check, ZIP CRC, ссылки вложений, размеры и хеши.
Поле `manifest.schema` — версия **формата backup**, не версия схемы application DB;
наличие REP-05 колонок и состояние миграции проверяются отдельно.

При подключённом offsite отправлять именно этот release-комплект, как описано в
runbook, без создания второй копии ради отправки. Статус Verified сам по себе не
доказывает доступность offsite или корректность Reports после миграции. Даже
успешный startup восстановленной копии подтверждает запуск, но не бизнес-семантику
Reports: отдельно сверить totals, категории, HTML/XLSX и REP-04.

При rollback приложения сохранить проверенный **NO-DELETE ops bundle** из runbook:
backup scripts/modules, действующие units/timers и минимальный read-only bridge
старому приложению. Не возвращать старые удаляющие backup scripts/units, не
выполнять blanket reset всего host checkout и не монтировать весь новый `src/`
поверх старого образа. Возврат касается версии приложения; SQLite, вложения,
backup sets, offsite-объекты и ops bundle сохраняются. Проверить running image,
закреплённые mount/hash и health/smoke согласно runbook. Любой restore БД остаётся
отдельной операцией с учётом новых записей после снимка.

## После отдельного одобрения владельца

1. Выполнить штатное обновление на утверждённый SHA; первый startup применит DDL
   и legacy-флаг. Наблюдать startup и исключить конкурирующую запись старой версии.
2. Проверить quick_check, точный running SHA, штатный health и HTTP smoke.
3. Проверить, что исходные события подтверждены с NULL metadata, число и сырые
   данные участий/связей/вложений не изменились. Reports сохраняет исходные totals;
   ожидаемое изменение категорий: завершённое связанное пустое/0 — непризовое,
   явный DNF — без результата. Проверить HTML/XLSX/REP-04 на безопасной выборке.
4. Проверить read-only доступ и отсутствие новых прав editor/viewer/athlete.
   Production-участия не создавать/не править для smoke.
5. Отчитаться: предыдущий/целевой/фактический SHA, backup и integrity, результат
   миграции, health/smoke, итоговое состояние и необходимость rollback.

## Совместимость и rollback

DDL аддитивен: старая версия читает таблицы и пишет новые события через DEFAULT 0.
Но старая версия не знает подтверждения: включает неподтверждённые события в
Reports, имеет прежнюю классификацию пустых мест/DNF и может снова автоматически
связывать NULL-историю при startup. Это функциональное
ограничение code rollback, которое нужно принять при решении об откате.

**Перед запуском старой версии:** остановить записи, сохранить свежую текущую БД
и вложения проверенным полным backup, затем read-only SQL оценить NULL-записи с
ровно одним точным кандидатом по `name + date + COALESCE(date_to, '')`. Не запускать
старый SQLiteAdapter ради этой оценки: его инициализация сама может записать связи.
Зафиксировать число кандидатов и совместимость конкретного старого image с текущей
БД. Аддитивный DDL сам по себе не делает такой rollback безопасным для истории.

Если число кандидатов больше нуля, **автоматический запуск старой версии запрещён
до отдельного решения владельца**: старый startup снова проставит NULL → event,
создав риск изменения данных и последующих Reports. Сохранить текущую БД/backup,
представить владельцу оценку и ждать решения; не выполнять массовый unlink и не
переназначать существующие ссылки. Если кандидатов нет и остальные проверки
совместимости прошли, при сбое startup/health вернуть разрешённую предыдущую
версию штатным способом и повторить health/smoke.

Не удалять новые колонки/метаданные и не сбрасывать флаги: сохранённая схема
позволяет повторно развернуть REP-05 без нового backfill. Если сбой внутри
SAVEPOINT — все три колонки и backfill откатываются вместе.

Восстановление БД — отдельная операция. Перед ним остановить записи, сохранить
текущую БД, проверить исходный backup, восстановить штатным способом, quick_check,
запуск и smoke. Если после снимка были новые записи, restore потеряет эти изменения;
требуется отдельное решение владельца. Вложения восстанавливаются согласованно с
выбранным снимком. Автоматический code rollback не означает restore БД.
